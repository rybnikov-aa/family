## 1. Назначение документа и подход (Specification Driven Development)

Документ — единый источник правды о поведении системы, построенный по практикам **Specification Driven Development**:

- **Спецификация впереди кода.** Любое поведение сначала описывается в спецификации (требование → критерий приёмки), затем реализуется в коде.
- **Проверяемое поведение.** Ключевые сценарии формулируются в форме **Given/When/Then** (в модульных спецификациях), что позволяет превратить их в автоматические тесты.
- **Трассируемость.** Каждое требование связано с критериями приёмки и местом реализации.
- **Источник регрессии.** Изменение поведения = сначала правка спецификации, затем кода.

Как использовать: при изменении требований, схемы конфига или API — сначала обновляется соответствующая модульная спецификация (а этот документ — если затрагиваются общие положения: конфигурация, API, архитектура), затем код. Код считается корректным, если удовлетворяет критериям приёмки из модульной спецификации.

## 2. Обзор системы

Семейное цифровое пространство — веб-портал, объединяющий документацию, архивы, фотографии, новости, планы и данные семьи. На главной странице выводится **динамический блок состояния сервисов**, отражающий доступность инфраструктуры (VPS-серверы и их сервисы). Весь портал закрыт авторизацией (FR-11): без действующей сессии фронтенд показывает экран входа, API отвечает 401.

- **Бэкенд** (`backend/`): Express 5 + Vite (`vite-plugin-node`), деплой под pm2. Отдаёт JSON API: health-эндпоинт, авторизацию (`/api/auth`) и проверку доступности VPS.
- **Фронтенд** (`frontend/`): React 19 + Vite + react-router-dom v7 (hash-роутинг). Тёмная/светлая/системная тема. Экран входа — `LoginPage`.

## 3. Требования

### 3.1. Источники требований (история формирования)

Требования добавлялись итеративно; ниже — хронология запросов и порождённых ими требований.

1. **Переделка блока stats** → динамический блок состояния сервисов; проверка состояния подключается позже; иконки — SVG.
2. **Иконки ThemeToggle** → SVG с сохранением цветов эмодзи (☀️→солнце, 🌙→луна, 🖥️→монитор).
3. **Реализация сервиса VPS** → замена сервиса `backend`; проверка доступности VPS выполняется на бэкенде; список VPS — в отдельном конфиг-файле.
4. **Структура конфига VPS** → поле `address` заменено на `ip`; секция `services[]` с полями `name`/`type`/`address`.
5. **Логика проверки** → сначала IP, затем сервисы; индикаторы: IP недоступен → красный; все сервисы доступны → зелёный; хоть один недоступен → жёлтый.
6. **Процент доступности** → вместо «online» показывать % доступности; цвет: 100% → зелёный, 90%<x<100% → жёлтый, иначе красный.
7. **Детализация** → клик по блоку доступности открывает форму с детализацией по каждой VPS.
8. **Отрисовка флага** → флаг картинкой (эмодзи-флаги на Windows отображаются как буквы «EU»).
9. **Доработки модалки** → индикаторы сервисов вместо текста, ссылка на панель управления (шестерёнка), IP + кнопка копирования, тултипы, выравнивание.
10. **Кнопка «Обновить»** → на главной у метрики доступности и в заголовке окна детализации.
11. **Исправление расчёта** → при недоступных сервисах, но доступном IP, VPS должна показывать 50%, а не 0%.
12. **Хранилище VPS → SQLite** → список VPS перенесён из `config/vps.json` в SQLite (`node:sqlite`); наполняется вручную, правки в рантайме без пересборки.
13. **Форма добавления VPS** → кнопка «+» в заголовке модалки детализации открывает форму добавления VPS (страна, имя, IP, панель, сервисы); `POST /api/vps` вставляет запись в SQLite и перечитывает список в памяти без рестарта.
14. **Импорт VPS из JSON** → кнопка импорта в шапке модалки детализации: выбор JSON-файла (структура как в `vps.json`), `POST /api/vps/import` добавляет записи пакетно (невалидные и дубликаты имён пропускаются).
15. **Удаление VPS** → кнопка-корзина на карточке VPS в детализации (справа от шестерёнки): подтверждение, `DELETE /api/vps/:name`, список статусов обновляется без рестарта.
16. **Раздел «Проекты»** → новые требования FR-10: отдельная страница «Проекты» + карточка на главной; проект = подпапка на сервере с `index.html`; список динамический (`GET /api/projects` — сканирование подпапок); страницы проектов используют общий шаблон `projects/` (стиль + тема приложения, общий `localStorage['theme']`).
17. **Авторизация** → новые требования FR-11: весь портал закрыт входом; несколько учёток с ролями (`admin`/`user`); вход/выход по httpOnly-cookie сессии (SQLite); админ-операции (добавление/удаление VPS, импорт, загрузка PDF) — только для роли `admin`.

### 3.2. Функциональные требования (по модулям)

Функциональные требования разбиты по функциональным разделам и описаны в соответствующих модульных спецификациях:

- **FR-1…FR-9** — [docs/specification-vps.md](specification-vps.md), раздел «Требования».
- **FR-10** — [docs/specification-projects.md](specification-projects.md), раздел «Требования».
- **FR-11** — [docs/specification-auth.md](specification-auth.md), раздел «Требования».

### 3.3. Нефункциональные требования

- **NFR-1. Доступность:** web-интерфейс рендерится, даже если бэкенд недоступен (блок показывает статус проверки, не падает).
- **NFR-2. Производительность:** результаты проверки VPS кэшируются на бэкенде (30 с) и дедуплицируются (in-flight); IP-проверка завершается по первой успешной пробе (короткое замыкание).
- **NFR-3. Адаптивность:** блок состояния и модалка адаптивны (grid/flex, перенос строк).
- **NFR-4. Доступность (a11y):** кликабельные карточки доступны с клавиатуры (Enter/Space), кнопки имеют `aria-label`, у иконок тултипы.
- **NFR-5. Конфигурируемость:** список VPS хранится в SQLite и меняется правкой БД без изменения кода и пересборки бандла.
- **NFR-6. Масштабируемость проектов:** список проектов сканируется с диска (кэш 60 с); новый проект = новая подпапка с `index.html`, без правок кода и пересборки.
- **NFR-7. Целостность деплоя:** при деплое существующие подпапки на сервере (в т.ч. проекты) не удаляются; перезаписываются только записи, присутствующие в репозитории (резервная копия не создаётся).
- **NFR-8. Безопасность авторизации:** пароли — только хэши scrypt (соль, constant-time сравнение); токен сессии в БД — только SHA-256, клиенту — в httpOnly `SameSite=Lax` cookie (`Secure` в проде); сессии имеют срок жизни и удаляются при выходе/протухании.

Ключевые принципы:

- **Презентация отделена от логики.** `ServiceStats` получает готовый список `ServiceStatus[]` и только рисует; источники данных — хуки.
- **Проверки — на бэкенде.** Фронтенд не знает, как проверяется доступность; он получает готовые статусы.
- **Конфигурация в SQLite.** Список VPS хранится в БД (`backend/data/vps.sqlite`), читается рантаймом; наполняется вручную (через SQL/клиент БД).

### 5.5. Конфигурация окружения (файлы `.env`)

В проекте три независимых пространства переменных окружения; у каждого — шаблон `.env.example` (в git) и, при необходимости, реальный `.env` (в git не попадает, реальные `.env` не переопределяют переменные уже заданные в окружении процесса):

| Файл            | Кто читает                             | Переменные                                                                                                                     |
| --------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Корневой `.env` | `scripts/deploy.mjs` (деплой)          | `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PORT`, `DEPLOY_FRONTEND_DIR`, `DEPLOY_BACKEND_DIR`, `DEPLOY_PM2_APP`, `DEPLOY_NODE_PATH` |
| `backend/.env`  | Бэкенд (`src/config/env.ts`, `dotenv`) | `PORT`, `CORS_ORIGIN`, `NODE_ENV`, `DB_PATH`, `PROJECTS_DIR`, `AUTH_COOKIE_NAME`, `SESSION_TTL_HOURS`, `AUTH_BOOTSTRAP_*`      |
| `frontend/.env` | Vite (только `VITE_*`)                 | `VITE_API_BASE_URL`                                                                                                            |

- **Корневой** `.env`/`.env.example` — конфигурация **деплоя** (SSH, пути на сервере, pm2).
- **`backend/.env`** — конфигурация **рантайма бэкенда**: `PORT` (по умолчанию `3000`), `CORS_ORIGIN` (dev `http://localhost:5173`, прод — домен), `NODE_ENV`, `DB_PATH` (по умолчанию `data/vps.sqlite`), `PROJECTS_DIR` (по умолчанию `../public_html/projects` — папка проектов, в которой подпапки с `index.html` считаются проектами и обслуживаются по `/projects/<slug>/`; в dev можно указать `../projects`), а также авторизация: `AUTH_COOKIE_NAME` (`sid`), `SESSION_TTL_HOURS` (168), `AUTH_BOOTSTRAP_PASSWORD`/`AUTH_BOOTSTRAP_USERNAME`/`AUTH_BOOTSTRAP_NAME` (создание первого администратора при старте, если в БД нет пользователей).
- **`frontend/.env`** — конфигурация **фронтенда**: `VITE_API_BASE_URL` (пусто → Vite dev-прокси `/api` → `:3000`).

## 8. Фронтенд

Здесь — инвентарь хуков/компонентов/иконок фронтенда (общий для портала). Поведение по модулям и их специфичные компоненты — в модульных спецификациях: VPS — [specification-vps.md](specification-vps.md), «Проекты» — [specification-projects.md](specification-projects.md), авторизация — [specification-auth.md](specification-auth.md).

### 8.1. Хуки

| Хук              | Назначение                                                                                                                                                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `useApiData`     | Базовый хук загрузки с одного API-эндпоинта: `{ data, error, loading, reload }`; защита от setState после размонтирования, `reload(next?)` — подмена fetcher (напр. `?refresh=1`). На нём построены `useVps`/`useProjects`/`useHealth`                                          |
| `useVps`         | Статусы VPS (`statuses`), ошибка (`error`), загрузка (`loading`), принудительное обновление (`refresh` → `fetchVps(true)` → `?refresh=1`) — на базе `useApiData`                                                                                                                |
| `useServices`    | Собирает блок состояния: `{ services: ServiceStatus[], vps: VpsStatus[], loading, refresh }`. В строке состояния только VPS-карточка: `{percent}%` доступности (цвет по состоянию); прочие статичные метрики убраны                                                             |
| `useHealth`      | Статус бэкенда (`/api/health`) — для футера и главной (на базе `useApiData`)                                                                                                                                                                                                    |
| `useProjects`    | Список проектов (`/api/projects`) для страницы «Проекты» (на базе `useApiData`)                                                                                                                                                                                                 |
| `useTheme`       | Тема light/dark/system (localStorage + `data-theme` на `<html>`)                                                                                                                                                                                                                |
| `useAuth`        | Авторизация: `{user, loading, login, logout, updateProfile}`; при старте проверяет сессию (`GET /api/auth/me`), при любом 401 (`auth:unauthorized`) сбрасывает пользователя к экрану входа; `updateProfile` сохраняет имя/пароль (`PATCH /api/auth/profile`) и обновляет `user` |
| `useEscapeClose` | Закрытие по Escape для модалок и оверлеев. `Modal` использует по умолчанию; `VpsAddModal` — со своей логикой «сначала редактор сервисов»                                                                                                                                        |

## 12. Решения и обоснования (ADR-lite)

| #      | Решение                                                                 | Альтернативы                                         | Обоснование                                                                                                                                                                             |
| ------ | ----------------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ADR-1  | Хранилище VPS — SQLite (`node:sqlite`)                                  | JSON/YAML/TOML/TS-файл, better-sqlite3               | Без новых зависимостей (встроенный `node:sqlite`); правки в рантайме без пересборки бандла; в будущем — история проверок                                                                |
| ADR-2  | Проверка VPS на бэкенде, фронт только рисует                            | Проверка на фронтенде                                | Единая точка проверки, кэш, доступ к сети из Node                                                                                                                                       |
| ADR-3  | Флаг — ISO-код страны + flagcdn                                         | Эмодзи-флаги                                         | Windows не рендерит эмодзи-флаги (показывает «EU» буквами)                                                                                                                              |
| ADR-4  | IP-проверка: базовые порты 22/443/80 + порты сервисов                   | Только порты сервисов                                | Развязка «машина жива» от «сервис работает» → IP доступен, сервис лежит = 50%, а не 0%                                                                                                  |
| ADR-5  | ocserv: TCP 443 + UDP/DTLS-проба                                        | Только TCP                                           | OpenConnect использует UDP/DTLS; TCP может быть закрыт при живом канале                                                                                                                 |
| ADR-6  | Кликабельная карточка VPS — `<div role="button">`, не `<button>`        | `<button>`                                           | Позволяет вложить кнопку «Обновить» (невалидно «button в button»)                                                                                                                       |
| ADR-7  | Кнопка «Обновить» — внутри карточки рядом со значением                  | Отдельная ячейка грида                               | Не ломает сетку статистики; интуитивно «рядом с метрикой»                                                                                                                               |
| ADR-8  | `fetchVps(force)` → `?refresh=1`                                        | Опрос по таймеру                                     | Явное действие пользователя, без лишнего трафика                                                                                                                                        |
| ADR-9  | Добавление VPS через UI/`POST /api/vps` + `reloadVpsEntries()`          | Только ручная правка БД                              | Редактирование состава мониторинга без SSH/SQL; список перечитывается в памяти без рестарта процесса                                                                                    |
| ADR-10 | Импорт VPS из JSON (`POST /api/vps/import`)                             | Вставка по одной через `POST /api/vps`               | Пакетная загрузка из файла одной операцией; невалидные и дубликаты имён пропускаются, результат — счётчиками                                                                            |
| ADR-11 | Проекты — статичные подпапки со сканированием `index.html`              | Отдельные SPA/iframe/динамические проекты            | «Проект = подпапка с index.html» — просто и независимо от стека; метаданные берутся из самого index.html; nginx не требует правок                                                       |
| ADR-12 | Авторизация — cookie-сессии (httpOnly, `SameSite=Lax`), сессии в SQLite | nginx Basic Auth, JWT в localStorage, OAuth (Google) | Весь портал за входом; cookie недоступна скриптам (в отличие от localStorage-JWT); сессии легко отзывать (выход/срок жизни); без внешних зависимостей; Basic Auth — без интеграции в UI |

## 13. Известные ограничения

- **HTTP-проверка** считает любой ответ (в т.ч. 4xx/5xx) за «доступен» — фиксируется факт ответа, а не корректность приложения.
- Для VPS без открытых базовых/сервисных портов возможен ложный «IP недоступен» (редкий кейс).
- Проценты округляются до целых (`Math.round`).
- При недоступности бэкенда блок показывает «офлайн» (красный), т.к. посчитать % не из чего.
- Флаг-картинки грузятся с внешнего CDN (flagcdn.com).
- **Тема и каркас проектов применяются ко всем страницам проекта**: `index.html` и подстраницы (`Reports/`, `estimate.html` и т.п.) используют общий шаблон `projects/` (`/projects/styles.css` + тема + иконки из `/projects/icon-sprite.svg`) с локальными табличными стилями (гибридный подход).
- Для работы `GET /api/projects` нужен доступ бэкенда к каталогу проектов (`PROJECTS_DIR`; по умолчанию `../public_html/projects` — подходит при стандартной раскладке каталогов).
- **Статичные страницы проектов (`/projects/**`) остаются публичными** — их раздаёт nginx напрямую, вне авторизации приложения (авторизация закрывает SPA и API). При необходимости закрыть — нужен отдельный механизм (например, nginx `auth_basic` на соответствующие `location`).

## 14. Карта файлов

**Бэкенд**

- `backend/src/app.ts` — монтаж роутов (`/api/health`, `/api/auth`, `/api/vps`, `/api/projects`); защита API (`requireAuth`), вызов bootstrap-администратора.
- `backend/src/config/vps.ts` — типы и экспорт `vpsEntries` (из БД) + `reloadVpsEntries()`.
- `backend/src/db/database.ts` — соединение SQLite (`node:sqlite`), схема.
- `backend/src/db/vpsRepository.ts` — чтение VPS из БД + `insertVpsEntry()` (вставка VPS и сервисов транзакцией).
- `backend/src/services/vpsChecker.ts` — IP-проверка + проверка сервисов + кэш.
- `backend/src/controllers/vpsController.ts`, `backend/src/routes/vps.ts` — эндпоинты GET (статусы), POST (добавление) и POST `/import` (импорт из JSON).
- `backend/src/controllers/healthController.ts`, `backend/src/routes/health.ts` — health.
- `backend/src/services/authService.ts` — пользователи, хэширование scrypt, сессии, bootstrap-администратор.
- `backend/src/middlewares/auth.ts` — `requireAuth`/`requireAdmin` (чтение httpOnly-cookie).
- `backend/src/controllers/authController.ts`, `backend/src/routes/auth.ts` — вход/выход/текущий пользователь.
- `backend/scripts/users.mjs` — CLI управления пользователями (`npm run user -w backend`: add/list/set-role/remove).
- `backend/src/services/projectsService.ts` — сканирование проектов (подпапки с `index.html`) + кэш.
- `backend/src/controllers/projectsController.ts`, `backend/src/routes/projects.ts` — `GET /api/projects`.
