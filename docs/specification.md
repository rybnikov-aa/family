## 1. Назначение документа и подход (Specification Driven Development)

Документ — единый источник правды о поведении системы, построенный по практикам **Specification Driven Development**:

- **Спецификация впереди кода.** Любое поведение сначала описывается здесь (требование → критерий приёмки), затем реализуется в коде.
- **Проверяемое поведение.** Ключевые сценарии формулируются в форме **Given/When/Then** (§11.12), что позволяет превратить их в автоматические тесты.
- **Трассируемость.** Каждое требование связано с критериями приёмки и местом реализации (§11.11).
- **Источник регрессии.** Изменение поведения = сначала правка спецификации, затем кода.

Как использовать: при изменении требований, схемы конфига или API — сначала обновляются §5–§9 и §11, затем код. Код считается корректным, если удовлетворяет критериям приёмки из §11.

## 2. Обзор системы

Семейное цифровое пространство — веб-портал, объединяющий документацию, архивы, фотографии, новости, планы и данные семьи. На главной странице выводится **динамический блок состояния сервисов**, отражающий доступность инфраструктуры (VPS-серверы и их сервисы).

- **Бэкенд** (`backend/`): Express 5 + Vite (`vite-plugin-node`), деплой под pm2. Отдаёт JSON API: health-эндпоинт и проверку доступности VPS.
- **Фронтенд** (`frontend/`): React 19 + Vite + react-router-dom v7 (hash-роутинг). Тёмная/светлая/системная тема.

## 3. Требования

### 3.1. Источники требований (история формирования)

Требования добавлялись итеративно; ниже — хронология запросов и порождённых ими требований.

1. **Переделка блока stats** → динамический блок состояния сервисов; проверка состояния подключается позже; иконки — SVG.
2. **Иконки ThemeToggle** → SVG с сохранением цветов эмодзи (☀️→солнце, 🌙→луна, 🖥️→монитор).
3. **Реализация сервиса VPS** → замена сервиса `backend`; проверка доступности VPS выполняется на бэкенде; список VPS — в отдельном конфиг-файле.
4. **Структура конфига VPS** → поле `address` заменено на `ip`; секция `services[]` с полями `name`/`type`/`address`.
5. **Логика проверки** → сначала IP, затем сервисы; индикаторы: IP недоступен → красный; все сервисы доступны → зелёный; хоть один недоступен → жёлтый.
6. **Процент доступности** → вместо «online» показывать % доступности; цвет: 100% → зелёный, 90%<x<100% → жёлтый, иначе красный.
7. **Детализация** → клик по блоку доступности открывает форму с детализацией по каждой VPS.
8. **Отрисовка флага** → флаг картинкой (эмодзи-флаги на Windows отображаются как буквы «EU»).
9. **Доработки модалки** → индикаторы сервисов вместо текста, ссылка на панель управления (шестерёнка), IP + кнопка копирования, тултипы, выравнивание.
10. **Кнопка «Обновить»** → на главной у метрики доступности и в заголовке окна детализации.
11. **Исправление расчёта** → при недоступных сервисах, но доступном IP, VPS должна показывать 50%, а не 0%.
12. **Хранилище VPS → SQLite** → список VPS перенесён из `config/vps.json` в SQLite (`node:sqlite`); наполняется вручную, правки в рантайме без пересборки.
13. **Форма добавления VPS** → кнопка «+» в заголовке модалки детализации открывает форму добавления VPS (страна, имя, IP, панель, сервисы); `POST /api/vps` вставляет запись в SQLite и перечитывает список в памяти без рестарта.
14. **Импорт VPS из JSON** → кнопка импорта в шапке модалки детализации: выбор JSON-файла (структура как в `vps.json`), `POST /api/vps/import` добавляет записи пакетно (невалидные и дубликаты имён пропускаются).
15. **Удаление VPS** → кнопка-корзина на карточке VPS в детализации (справа от шестерёнки): подтверждение, `DELETE /api/vps/:name`, список статусов обновляется без рестарта.
16. **Раздел «Проекты»** → новые требования FR-10: отдельная страница «Проекты» + карточка на главной; проект = подпапка на сервере с `index.html`; список динамический (`GET /api/projects` — сканирование подпапок); страницы проектов используют общий шаблон `projects/` (стиль + тема приложения, общий `localStorage['theme']`).

### 3.2. Функциональные требования

**FR-1. Блок состояния сервисов (главная страница).**

- 1.1 Блок динамический и отражает актуальное состояние сервисов.
- 1.2 Архитектура позволяет подключать реальные проверки позже без изменения компонента отрисовки.
- 1.3 Все иконки в блоке — SVG (без эмодзи).

**FR-2. Сервис VPS.**

- 2.1 Сервис с id `backend` заменён на сервис `vps`.
- 2.2 Проверка доступности VPS выполняется на бэкенде (`GET /api/vps`).
- 2.3 Список VPS хранится в SQLite на бэкенде (наполняется вручную).
- 2.4 Каждая запись VPS содержит: страну (ISO-код), отображаемое имя, IP, ссылку на панель хостера, список сервисов.

**FR-3. Проверка доступности VPS.**

- 3.1 Сначала проверяется доступность по IP.
- 3.2 Если IP недоступен — проверка останавливается, индикатор красный.
- 3.3 Если IP доступен — проверяются сервисы.
- 3.4 Все сервисы доступны → зелёный; хотя бы один недоступен → жёлтый.
- 3.5 Поддерживаемые типы сервисов: `http` (HTTP(S) GET), `ocserv` (OpenConnect VPN: TCP TLS + UDP/DTLS).

**FR-4. Процент доступности.**

- 4.1 Отображается % доступности (не «online»/«offline»).
- 4.2 Формулы (см. §7).
- 4.3 Цвет индикатора по проценту: 100% → зелёный; 90%<x<100% → жёлтый; иначе → красный.

**FR-5. Детализация.**

- 5.1 Клик по карточке VPS открывает модальное окно «Доступность VPS».
- 5.2 Модалка показывает детализацию по каждой VPS: флаг-картинка, имя, процент доступности (в заголовке, цвет по состоянию), IP (под заголовком, выровнен по левому краю с именем, фиксированный отступ), кнопка копирования IP (справа от IP), ссылка на панель (шестерёнка) и кнопка удаления (в углу заголовка); сервисы — с латенцией в мс.
- 5.3 Список сервисов VPS: имя — ссылка на сервис, рядом цветной индикатор (зелёный/красный).
- 5.4 Закрытие модалки: крестик, клик по подложке, Escape.
- 5.5 Карточки VPS — сетка в 2 столбца (на узких экранах — 1 столбец).
- 5.6 Кнопка-корзина на карточке: подтверждение → `DELETE /api/vps/:name` (204); после удаления список статусов обновляется (без рестарта); несуществующее имя → 404.

**FR-6. Кнопка «Обновить».**

- 6.1 Кнопка на главной рядом со значением доступности VPS.
- 6.2 Кнопка в заголовке окна детализации.
- 6.3 Клик форсирует перепроверку на бэкенде (обход кэша); во время проверки иконка вращается, кнопка disabled.

**FR-7. Тема и иконки.**

- 7.1 Переключатель темы (light/dark/system) — иконки SVG с сохранением цветов исходных эмодзи.
- 7.2 Иконки разделов и блока состояния — SVG.

**FR-8. Форма добавления VPS.**

- 8.1 В заголовке модалки «Доступность VPS» рядом с кнопкой «Обновить» есть кнопка «+».
- 8.2 Клик по «+» открывает форму добавления VPS на мониторинг.
- 8.3 Поля формы: Расположение (выпадающий список стран), Имя, IP, Панель управления.
- 8.4 Поле «Сервисы» — набор сервисов, редактируемый по кнопке с троеточием в этом поле (добавление/удаление/правка name, type, address).
- 8.5 Сохранение отправляет `POST /api/vps`; после успешного добавления форма закрывается и список статусов принудительно обновляется.

**FR-9. Импорт VPS из JSON.**

- 9.1 В шапке модалки «Доступность VPS» есть кнопка импорта из JSON-файла.
- 9.2 Формат файла — как в `vps.json`: `{ "vps": [ {country, name, ip, panel, services[]} ] }` (допускается и голый массив).
- 9.3 После выбора файла записи отправляются `POST /api/vps/import`; результат (импортировано/пропущено) показывается в модалке.
- 9.4 Невалидные записи и дубликаты имён пропускаются без остановки импорта; список статусов после импорта обновляется.

**FR-10. Раздел «Проекты».**

- 10.1 Проект — это подпапка на сервере (в каталоге `PROJECTS_DIR`) с файлом `index.html`.
- 10.2 Список проектов динамический: `GET /api/projects` сканирует подпапки `PROJECTS_DIR` и возвращает метаданные (`slug`, `title`, `description`, `accent`, `url`, `order`).
- 10.3 Метаданные берутся из самого `index.html` проекта: `<title>`, `<meta name="project-title">`, `<meta name="description">`, `<meta name="project-accent">`, `<meta name="project-icon">`, `<meta name="project-order">`.
- 10.4 На главной есть карточка «Проекты», ведущая на страницу `#/projects`.
- 10.5 Страница «Проекты» показывает список проектов карточками (иконка по `project-icon`, акцентный цвет из метаданных); карточка — ссылка на подпапку проекта (`/<slug>/`).
- 10.6 Страницы проектов наследуют стиль и тему приложения (общий шаблон `projects/`); тема хранится в `localStorage['theme']` (общая для домена) и сохраняется при переходе между приложением и проектами.
- 10.7 Проекты деплоятся из папки `projects/` репозитория в `public_html/<slug>/` (служебные папки `_*` не деплоятся); существующие подпапки на сервере не удаляются, перед перезаписью создаётся резервная копия.

### 3.3. Нефункциональные требования

- **NFR-1. Доступность:** web-интерфейс рендерится, даже если бэкенд недоступен (блок показывает статус проверки, не падает).
- **NFR-2. Производительность:** результаты проверки VPS кэшируются на бэкенде (30 с) и дедуплицируются (in-flight); IP-проверка завершается по первой успешной пробе (короткое замыкание).
- **NFR-3. Адаптивность:** блок состояния и модалка адаптивны (grid/flex, перенос строк).
- **NFR-4. Доступность (a11y):** кликабельные карточки доступны с клавиатуры (Enter/Space), кнопки имеют `aria-label`, у иконок тултипы.
- **NFR-5. Конфигурируемость:** список VPS хранится в SQLite и меняется правкой БД без изменения кода и пересборки бандла.
- **NFR-6. Масштабируемость проектов:** список проектов сканируется с диска (кэш 60 с); новый проект = новая подпапка с `index.html`, без правок кода и пересборки.
- **NFR-7. Целостность деплоя:** при деплое существующие подпапки на сервере (в т.ч. проекты) не удаляются; перед перезаписью папок проектов из репозитория создаётся резервная копия `/tmp/family-projects-backup-<timestamp>`.

## 5. Данные и конфигурация

### 5.1. Хранилище VPS — SQLite (`backend/data/vps.sqlite`)

Список VPS хранится в **SQLite** (встроенный модуль `node:sqlite`, без новых зависимостей — в духе изначального выбора JSON). Файл БД лежит по пути из `env.DB_PATH` (по умолчанию `data/vps.sqlite` рядом с бэкендом), не попадает в git и не затирается при деплое.

Схема (см. `backend/src/db/database.ts`):

```sql
CREATE TABLE vps (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,
  country TEXT NOT NULL,
  name    TEXT NOT NULL UNIQUE,
  ip      TEXT NOT NULL,
  panel   TEXT NOT NULL
);

CREATE TABLE vps_services (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,
  vps_id  INTEGER NOT NULL REFERENCES vps(id) ON DELETE CASCADE,
  name    TEXT NOT NULL,
  type    TEXT NOT NULL,
  address TEXT NOT NULL
);
```

### 5.2. Наполнение БД

БД наполняется вручную (SQL-скриптом или клиентом SQLite), через форму добавления VPS в UI (`POST /api/vps`) либо импортом из JSON-файла структуры `vps.json` (`POST /api/vps/import`). Схема таблиц создаётся автоматически при первом обращении (`CREATE TABLE IF NOT EXISTS` в `database.ts`). Пример вставки:

```sql
INSERT INTO vps (country, name, ip, panel) VALUES ('nl', 'jhnl', '150.251.139.253', 'https://my.justhost.asia/');
INSERT INTO vps_services (vps_id, name, type, address)
  VALUES (last_insert_rowid(), '3x-ui', 'http', 'https://jhnl.rybnikov.su:51981/qaVfkyoyQYaK6VoMgM');
```

### 5.3. Схема записи VPS

| Поле                 | Тип    | Описание                                                                                                      |
| -------------------- | ------ | ------------------------------------------------------------------------------------------------------------- |
| `country`            | string | ISO-код страны для флага (напр. `eu`, `nl`, `de`); рендерится картинкой с `https://flagcdn.com/{country}.svg` |
| `name`               | string | Отображаемое имя VPS (уникальное)                                                                             |
| `ip`                 | string | IP-адрес для проверки доступности                                                                             |
| `panel`              | string | Ссылка на панель управления хостера                                                                           |
| `services[]`         | array  | Список сервисов                                                                                               |
| `services[].name`    | string | Отображаемое имя сервиса (напр. `3x-ui`)                                                                      |
| `services[].type`    | string | Тип проверки: `http` / `ocserv`                                                                               |
| `services[].address` | string | Адрес для проверки (URL или хост:порт)                                                                        |

### 5.4. Типы (бэкенд, `config/vps.ts`)

- `VpsEntry` — запись конфига (country, name, ip, panel, services).
- `VpsServiceConfig` — конфигурация сервиса (name, type, address).
- `VpsStatus extends VpsEntry` — результат проверки VPS (+ `online`, `latencyMs`, `error`, `checkedAt`, `services[]`).
- `VpsServiceStatus` — результат проверки сервиса (+ `online`, `latencyMs`, `error`).
- Загрузка: `vpsEntries` читается из БД через `db/vpsRepository.ts` при старте модуля; после `POST /api/vps` вызывается `reloadVpsEntries()` (перечитывание в памяти без рестарта).

### 5.5. Конфигурация окружения (файлы `.env`)

В проекте три независимых пространства переменных окружения; у каждого — шаблон `.env.example` (в git) и, при необходимости, реальный `.env` (в git не попадает, реальные `.env` не переопределяют переменные уже заданные в окружении процесса):

| Файл            | Кто читает                             | Переменные                                                                                                                     |
| --------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Корневой `.env` | `scripts/deploy.mjs` (деплой)          | `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PORT`, `DEPLOY_FRONTEND_DIR`, `DEPLOY_BACKEND_DIR`, `DEPLOY_PM2_APP`, `DEPLOY_NODE_PATH` |
| `backend/.env`  | Бэкенд (`src/config/env.ts`, `dotenv`) | `PORT`, `CORS_ORIGIN`, `NODE_ENV`, `DB_PATH`, `PROJECTS_DIR`                                                                   |
| `frontend/.env` | Vite (только `VITE_*`)                 | `VITE_API_BASE_URL`                                                                                                            |

- **Корневой** `.env`/`.env.example` — конфигурация **деплоя** (SSH, пути на сервере, pm2).
- **`backend/.env`** — конфигурация **рантайма бэкенда**: `PORT` (по умолчанию `3000`), `CORS_ORIGIN` (dev `http://localhost:5173`, прод — домен), `NODE_ENV`, `DB_PATH` (по умолчанию `data/vps.sqlite`), `PROJECTS_DIR` (по умолчанию `../public_html` — каталог, в котором подпапки с `index.html` считаются проектами; в dev можно указать `../projects`).
- **`frontend/.env`** — конфигурация **фронтенда**: `VITE_API_BASE_URL` (пусто → Vite dev-прокси `/api` → `:3000`).

## 6. Бэкенд

### 6.1. API

| Метод | Путь              | Назначение                                      | Параметры                                                                                   |
| ----- | ----------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------- |
| GET   | `/api/health`     | Здоровье бэкенда                                | —                                                                                           |
| GET   | `/api/projects`   | Список проектов (подпапки с `index.html`)       | —                                                                                           |
| GET   | `/api/vps`        | Статусы доступности всех VPS + их сервисов      | `refresh=1` — форсированная перепроверка (обход кэша)                                       |
| POST  | `/api/vps`        | Добавить VPS на мониторинг                      | Тело — `VpsEntry` (`{country, name, ip, panel, services[]}`)                                |
| POST  | `/api/vps/import` | Импорт VPS из JSON (структура как в `vps.json`) | Тело — `{ "vps": [VpsEntry, …] }` (или голый массив); ответ — `{imported, skipped, errors}` |

```json
    "online": true,
    "latencyMs": 85,
    "error": null,
    "checkedAt": "2026-08-05T…",
    "services": [
      {
        "name": "3x-ui",
        "type": "http",
        "address": "…",
        "online": true,
        "latencyMs": 456,
        "error": null
      }
    ]
  }
]
```

### 6.2. Проверка доступности (`services/vpsChecker.ts`)

**Шаг 1 — IP-проверка (`checkIp`):**

- Пробы параллельно (таймаут 3 с каждая):
  - **Базовые «машина жива»**: TCP 22 (SSH), 443, 80 — не зависят от сервисов.
  - **Порты/протоколы сервисов**: `http` → TCP на порт адреса; `ocserv` → TCP 443 (по умолчанию) **и** UDP/DTLS-проба.
- `anySucceeds()` — короткое замыкание: доступен, как только любая проба успешна.
- Если IP недоступен → `online: false`, сервисы не проверяются (красный индикатор).

**Шаг 2 — Сервисы:**

- `http`: HTTP(S) GET, таймаут 5 с; любой HTTP-ответ (в т.ч. 4xx/5xx) = доступен.
- `ocserv`: TCP 443 (TLS); при неудаче — UDP/DTLS-проба (минимальный DTLS ClientHello; любой ответный датаграмм = канал жив).
- Неизвестный тип → `online: false` с ошибкой «Неподдерживаемый тип проверки».

**Кэширование:** результат кэшируется 30 с (TTL); параллельные запросы дедуплицируются (in-flight promise); `refresh=1` форсирует перепроверку.

### 6.3. Запуск

- Dev: `npm run dev --workspace backend` (Vite + vite-plugin-node, порт 3000, `NODE_ENV=development`).
- Prod: сборка Vite, запуск под pm2 (`NODE_ENV=production`; nginx проксирует `/api/` → `127.0.0.1:3000` без слэша).

### 6.4. Сканирование проектов (`services/projectsService.ts`)

- Каталог — `env.PROJECTS_DIR` (по умолчанию `../public_html` относительно каталога бэкенда).
- Сканируются непосредственные подпапки, содержащие `index.html`; служебные/скрытые (`_*`, `.*`) пропускаются.
- Метаданные из самого `index.html`: `title`/`project-title`, `description`, `project-accent` (по умолчанию `#3b82f6`), `project-icon` (по умолчанию пусто — иконка по умолчанию), `project-order` (по умолчанию — в конец списка).
- Сортировка: по `project-order`, затем по названию (ru).
- Результат кэшируется 60 с.

Формат ответа `GET /api/projects`:

```json
[
  {
    "slug": "renovation",
    "title": "Ремонт",
    "description": "Отчётность по ремонту: смета, внесённые средства, отчёты о работах и материалах.",
    "accent": "#e8872e",
    "url": "/renovation/",
    "order": 0
  }
]
```

## 7. Логика расчёта доступности (`frontend/src/utils/availability.ts`)

Формулы (все доли 0..1, на экран — `Math.round(x * 100)` %):

$$
\text{availability}(VPS) = \text{ipAvailability}(VPS) \cdot 0.5 + \text{servicesAvailability}(VPS) \cdot 0.5
$$

$$
\text{servicesAvailability}(VPS) = \frac{\sum_{s \in services} [s \text{ доступен}]}{|\text{services}|}
$$

$$
\text{overall} = \frac{\sum_{v \in VPS} \text{availability}(v)}{|\text{VPS}|}
$$

Правила:

- `ipAvailability` = 1, если `online` (IP доступен), иначе 0.
- `servicesAvailability` = доля доступных сервисов; если сервисов нет — 0.
- **Критично:** при доступном IP и недоступных сервисах доступность VPS = **50%** (а не 0%). Это обеспечивается тем, что IP-проверка использует базовые «живые» порты и не зависит от состояния конкретного сервиса.

Цвет индикатора по проценту:

| Процент        | Состояние | Цвет    |
| -------------- | --------- | ------- |
| 100%           | `ok`      | зелёный |
| 90% < x < 100% | `warning` | жёлтый  |
| ≤ 90%          | `error`   | красный |

Состояния `ServiceState`: `ok | warning | error | checking | unknown`.

## 9. Поведение и взаимодействие (UX)

### 9.1. Главная страница

- Блок «Состояние сервисов»: 4 карточки (дата регистрации, активных раздела, проектов, **VPS**).
- Карточка **VPS**:
  - Значение — процент доступности (напр. «100%»), цвет индикатора по §7.
  - Кнопка «Обновить» — сразу рядом со значением (внутри карточки, `.stat-item__value-row`), не ломает сетку.
  - Клик по карточке (вне кнопки) — открывает детализацию; клик по «Обновить» — только перепроверка (без открытия модалки).
- Во время проверки: значение «проверка…», кнопка «Обновить» disabled с вращающейся иконкой.

### 9.2. Модалка детализации

- Заголовок: «Доступность VPS», справа — кнопки «+» (добавить VPS), «Обновить» и «Закрыть».
- Сводка: общая доступность.
- Карточки VPS выстроены в **сетку в 2 столбца** (на узких экранах — 1 столбец). В каждой карточке (грид: колонка флага-рейла + колонка контента):
  - строка «заголовок»: имя; справа — процент доступности, выделенный цветным фоном (pill, цвет по состоянию: зелёный/жёлтый/красный), и на отступе 16px (2×8) — шестерёнка (панель) и корзина (удаление);
  - строка «соединение» (всегда на фиксированном отступе 6px под заголовком, выровнена по левому краю с именем): IP-адрес (моноширинный) + кнопка копирования;
  - строка «сервисы»: точка-статус, имя (ссылка для HTTP), латенция в мс.
- Строки карточки не растягиваются по высоте (`align-content: start`) — IP всегда прижат к заголовку (не «плавает» по центру пустого пространства).
- Сервисы: имя — ссылка (открывается в новой вкладке), рядом цветная точка и латенция (мс).
- Тултипы у иконок (копировать/панель/удаление) — на CSS (`data-tooltip`).

### 9.3. Форма добавления VPS

- Открывается по кнопке «+» в заголовке модалки детализации (содержимое модалки заменяется формой).
- Поля: **Расположение** (выпадающий список стран), **Имя**, **IP**, **Панель управления** — текстовые поля.
- Поле **«Сервисы»**: набор сервисов в виде чипов; кнопка с троеточием в этом поле открывает редактор сервисов (добавление/удаление/правка имени, типа `http`/`ocserv`, адреса). В редакторе у каждого сервиса **имя и тип — на одной строке** (пропорция 4:3, грид), **адрес — на отдельной строке** (правые границы типа и адреса совпадают); **кнопка удаления — корзина** в правой колонке.
- «Добавить» → `POST /api/vps`; пустые сервисы отбрасываются. После успеха — форма закрывается, список статусов принудительно обновляется (`?refresh=1`).
- «Отмена» / крестик / Escape — закрытие без сохранения; при открытом редакторе сервисов Escape сначала закрывает его.

### 9.4. Импорт VPS из JSON

- Кнопка импорта в шапке модалки детализации открывает диалог выбора JSON-файла (структура как в `vps.json`).
- Файл разбирается на клиенте (невалидные записи отбрасываются), затем `POST /api/vps/import` добавляет записи пакетно.
- В модалке показывается результат: «Импортировано: N; пропущено: M» + список причин пропуска; после импорта список статусов обновляется.

### 9.5. Раздел «Проекты»

- На главной в сетке разделов — карточка «Проекты» (каталог), ведущая на `#/projects`.
- Раздел «Ремонт» на главной убран (переехал в «Проекты»): карточка в сетке, метрика в статусах, кнопка в шапке и ссылка в футере удалены; проект «Ремонт» доступен через «Проекты» и отображается с иконкой-ключом (как у прежнего раздела).
- Страница «Проекты»: заголовок «Проекты» + сетка карточек проектов (иконка по `project-icon`, название, описание, акцентный цвет из метаданных); карточка — ссылка на подпапку проекта (`/<slug>/`).
- Состояния страницы: загрузка («Загрузка проектов…»), ошибка (бэкенд недоступен), пустой список («Проектов пока нет»).
- В шапке и футере приложения — пункт меню «Проекты».

## 10. Тема и роутинг

- Роутинг — react-router-dom v7 `createHashRouter` (обязательно hash: nginx без SPA-fallback). Константы в `routes.ts`; catch-all → главная.
- Тема: `useTheme` + инлайн-скрипт в `index.html` (без «мигания»); все цвета — CSS-переменные в `:root` и `[data-theme='dark']`.
- Страницы проектов (статичные `index.html` в подпапках) наследуют тему приложения: тот же inline-скрипт в `<head>` + `/projects/theme.js`, общий `localStorage['theme']`; общие стили — `/projects/styles.css` (те же CSS-переменные), акцентный цвет проекта — `--project-accent` (задаётся в `index.html` проекта).

## 11. Критерии приёмки

### 11.1. Блок состояния сервисов

- [ ] Блок отображает актуальные статусы сервисов и не падает при недоступном бэкенде.
- [ ] Все иконки — SVG (нет эмодзи в блоке).
- [ ] Карточки в блоке одинаковой ширины; добавление кнопки «Обновить» не нарушает сетку.
- [ ] В блоке есть карточка «проектов» с количеством проектов из `GET /api/projects` (во время загрузки — «проверка…», при недоступном бэкенде — «—»); подпись-ссылка ведёт на `#/projects`.

### 11.2. Сервис VPS

- [ ] В блоке есть карточка VPS (заменяет прежний «бэкенд»).
- [ ] Список VPS хранится в SQLite (`backend/data/vps.sqlite`); правка БД меняет проверку без изменения кода и пересборки.
- [ ] Каждая запись содержит `country`, `name`, `ip`, `panel`, `services[]`.

### 11.3. Проверка доступности

- [ ] `GET /api/vps` возвращает статусы VPS и сервисов.
- [ ] Если IP недоступен — `online: false`, сервисы не проверяются (красный).
- [ ] Если IP доступен и все сервисы доступны — зелёный.
- [ ] Если IP доступен и хотя бы один сервис недоступен — жёлтый.
- [ ] `refresh=1` форсирует перепроверку (обход 30-с кэша).

### 11.4. Процент доступности

- [ ] Отображается % (не «online»).
- [ ] Формулы §7 реализованы корректно.
- [ ] **Регрессия:** при доступном IP и недоступных сервисах VPS = **50%** (не 0%).
- [ ] Цвет: 100% — зелёный, 90<x<100 — жёлтый, ≤90 — красный.

### 11.5. Детализация

- [ ] Клик по карточке VPS открывает модалку.
- [ ] Флаг — картинка (не буквы).

- [ ] IP выровнен по левому краю с именем и на фиксированном отступе под заголовком; копирование — справа от IP; шестерёнка и удаление — в углу заголовка.
- [ ] Сервисы: точка-статус, имя (ссылка для HTTP) и латенция в мс.
- [ ] Карточки VPS — сетка в 2 столбца (на узких экранах — 1 столбец).
- [ ] Закрытие: крестик / подложка / Escape.

### 11.8. Форма добавления VPS

### 11.12. Поведенческие сценарии (Given/When/Then)

**S1. IP недоступен → красный индикатор.**

- Given: VPS, у которого IP не отвечает ни на одной пробе (TCP 22/443/80 и порты сервисов)
- When: выполняется `GET /api/vps`
- Then: `online: false`, сервисы не проверяются, доступность VPS = 0%, индикатор красный (`error`)

**S2. IP доступен, сервисы недоступны → 50%.**

- Given: VPS с доступным IP (например, по SSH 22), но недоступными сервисами
- When: выполняется `GET /api/vps` и расчёт доступности
- Then: доступность VPS = 50% (IP*0.5 + 0*0.5); цвет индикатора — по правилу §7 (красный, т.к. ≤90%)

**S3. Всё доступно → 100% зелёный.**

- Given: все VPS доступны по IP и все сервисы доступны
- When: выполняется расчёт доступности
- Then: общий процент = 100%, индикатор зелёный (`ok`)

**S4. Открытие детализации.**

- Given: главная страница с блоком состояния
- When: пользователь кликает по карточке VPS (не по кнопке «Обновить»)
- Then: открывается модалка «Доступность VPS» с детализацией по каждой VPS

**S5. Кнопка «Обновить» на главной не открывает модалку.**

- Given: главная страница, карточка VPS со значением % и кнопкой «Обновить»
- When: пользователь кликает по кнопке «Обновить»
- Then: выполняется принудительная перепроверка (`?refresh=1`), значение переходит в «проверка…», кнопка disabled с вращением; модалка НЕ открывается

**S6. Копирование IP.**

- Given: открыта модалка детализации
- When: пользователь кликает по кнопке копирования IP
- Then: IP записан в буфер обмена, иконка меняется на галочку на 1.5 с

**S7. Флаг — картинка.**

- Given: открыта модалка детализации
- Then: флаг отображается изображением `https://flagcdn.com/{country}.svg`, а не текстом/буквами

**S8. Добавление VPS через форму.**

- Given: открыта модалка детализации
- When: пользователь нажимает «+», заполняет форму (страна, имя, IP, сервисы) и нажимает «Добавить»
- Then: отправляется `POST /api/vps`, VPS появляется в списке мониторинга (форма закрывается, статусы обновляются принудительно)

**S9. Добавление VPS с занятым именем.**

- Given: в БД уже есть VPS с именем `X`
- When: пользователь добавляет VPS с тем же именем `X`
- Then: сервер возвращает 409, форма показывает понятную ошибку, запись не дублируется

**S10. Импорт VPS из JSON.**

- Given: открыта модалка детализации
- When: пользователь выбирает JSON-файл (структура как в `vps.json`) и подтверждает импорт
- Then: отправляется `POST /api/vps/import`, новые VPS появляются в списке, в модалке виден результат (импортировано/пропущено)

**S11. Удаление VPS.**

- Given: открыта модалка детализации, карточка VPS
- When: пользователь нажимает корзину и подтверждает удаление
- Then: отправляется `DELETE /api/vps/:name`, карточка исчезает, список статусов обновляется принудительно

**S12. Отмена удаления VPS.**

- Given: открыта модалка детализации
- When: пользователь нажимает корзину и отменяет подтверждение
- Then: запрос `DELETE` не отправляется, VPS остаётся в списке

**S13. Открытие раздела «Проекты».**

- Given: главная страница портала
- When: пользователь открывает `#/projects` (или кликает карточку «Проекты»)
- Then: отображается список проектов, полученный от `GET /api/projects`; проект «Ремонт» — первым

**S14. Тема сохраняется при переходе в проект.**

- Given: в приложении выбрана тема (например, тёмная), `localStorage['theme']='dark'`
- When: пользователь открывает подпапку проекта (например, `/renovation/`)
- Then: страница проекта отрисовывается в той же теме (`data-theme='dark'`); переключение темы на странице проекта меняет тему и в приложении

**S15. Новый проект без правок кода.**

- Given: на сервере в `PROJECTS_DIR` создана подпапка `new-project/` с `index.html` (с мета-тегами)
- When: выполняется `GET /api/projects` (мимо 60-с кэша)
- Then: проект появляется в списке; деплой из репозитория при этом не требуется

## 12. Решения и обоснования (ADR-lite)

| #      | Решение                                                          | Альтернативы                              | Обоснование                                                                                                                       |
| ------ | ---------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| ADR-1  | Хранилище VPS — SQLite (`node:sqlite`)                           | JSON/YAML/TOML/TS-файл, better-sqlite3    | Без новых зависимостей (встроенный `node:sqlite`); правки в рантайме без пересборки бандла; в будущем — история проверок          |
| ADR-2  | Проверка VPS на бэкенде, фронт только рисует                     | Проверка на фронтенде                     | Единая точка проверки, кэш, доступ к сети из Node                                                                                 |
| ADR-3  | Флаг — ISO-код страны + flagcdn                                  | Эмодзи-флаги                              | Windows не рендерит эмодзи-флаги (показывает «EU» буквами)                                                                        |
| ADR-4  | IP-проверка: базовые порты 22/443/80 + порты сервисов            | Только порты сервисов                     | Развязка «машина жива» от «сервис работает» → IP доступен, сервис лежит = 50%, а не 0%                                            |
| ADR-5  | ocserv: TCP 443 + UDP/DTLS-проба                                 | Только TCP                                | OpenConnect использует UDP/DTLS; TCP может быть закрыт при живом канале                                                           |
| ADR-6  | Кликабельная карточка VPS — `<div role="button">`, не `<button>` | `<button>`                                | Позволяет вложить кнопку «Обновить» (невалидно «button в button»)                                                                 |
| ADR-7  | Кнопка «Обновить» — внутри карточки рядом со значением           | Отдельная ячейка грида                    | Не ломает сетку статистики; интуитивно «рядом с метрикой»                                                                         |
| ADR-8  | `fetchVps(force)` → `?refresh=1`                                 | Опрос по таймеру                          | Явное действие пользователя, без лишнего трафика                                                                                  |
| ADR-9  | Добавление VPS через UI/`POST /api/vps` + `reloadVpsEntries()`   | Только ручная правка БД                   | Редактирование состава мониторинга без SSH/SQL; список перечитывается в памяти без рестарта процесса                              |
| ADR-10 | Импорт VPS из JSON (`POST /api/vps/import`)                      | Вставка по одной через `POST /api/vps`    | Пакетная загрузка из файла одной операцией; невалидные и дубликаты имён пропускаются, результат — счётчиками                      |
| ADR-11 | Проекты — статичные подпапки со сканированием `index.html`       | Отдельные SPA/iframe/динамические проекты | «Проект = подпапка с index.html» — просто и независимо от стека; метаданные берутся из самого index.html; nginx не требует правок |

## 13. Известные ограничения

- **HTTP-проверка** считает любой ответ (в т.ч. 4xx/5xx) за «доступен» — фиксируется факт ответа, а не корректность приложения.
- Для VPS без открытых базовых/сервисных портов возможен ложный «IP недоступен» (редкий кейс).
- Проценты округляются до целых (`Math.round`).
- При недоступности бэкенда блок показывает «офлайн» (красный), т.к. посчитать % не из чего.
- Флаг-картинки грузятся с внешнего CDN (flagcdn.com).
- **Тема проектов применяется только к `index.html` проекта** (общий шаблон `projects/`); подстраницы проекта (например, `Reports/`, `estimate.html`) пока в собственном стиле — при необходимости их нужно переводить на шаблон отдельно.
- Для работы `GET /api/projects` нужен доступ бэкенда к каталогу проектов (`PROJECTS_DIR`; по умолчанию `../public_html` — подходит при стандартной раскладке каталогов).
