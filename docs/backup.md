# Бэкап и восстановление

Справочник по резервному копированию основного сервера (`my.rybnikov.su`) и восстановлению
сайта из бэкапа (например, на новый VPS). Реализация — `scripts/backup.mjs` (`npm run backup`)
и `scripts/restore.mjs` (`npm run restore`).

Бэкап сохраняет **невосстановимое из git** — runtime-данные приложения. Код (frontend/backend +
`node_modules`) в архив **не входит** и восстанавливается штатным `npm run deploy`.

---

## 1. Что входит в архив

| Что                              | Источник на сервере                                                       |
| -------------------------------- | ------------------------------------------------------------------------- |
| 5 SQLite-БД (+ WAL/SHM)          | `server/data/` (vps, auth, projects, renovation, diary)                   |
| PDF «Ремонта»                    | `server/docs/renovation/` (в т.ч. подпапки `design/`, `legacy/`)          |
| Фото событий «Дневника»          | `server/images/` (уникальная папка на событие + `thumbs/`)                |
| Рантайм-конфиг бэкенда           | `server/.env`                                                             |
| Справочно (НЕ восстанавливается) | `server-config/` — nginx-vhost'ы + letsencrypt (образец для нового хоста) |

Дополнительно в архиве: `MANIFEST.txt` (метаданные: дата, хост, список файлов) и `*.sha256`
(контрольная сумма архива).

**Что НЕ бэкапится** (восстанавливается иначе):

- Код приложения → `npm run deploy`;
- nginx-vhost'ы и SSL (letsencrypt) → **хостозависимые** (домен, пути, сертификаты), при переезде
  пересоздаются, а не «восстанавливаются»; конфиги из `server-config/` архива — только образец;
- статичный архив `projects/` репозитория — история, не деплоится и не бэкапится.

## 2. Создание бэкапа

```powershell
npm run backup                      # архив на сервере + скачивание в backups/ + сверка sha256
npm run backup -- --local D:\backup # скачивание в конкретную локальную папку
npm run backup -- --remote-only     # оставить архив только на сервере
npm run backup -- --install-cron    # ежедневный cron-бэкап на сервере (идемпотентно)
npm run backup -- --print-script    # показать генерируемый remote-скрипт (без сети)
npm run backup -- --print-config    # показать итоговую конфигурацию
```

Поведение:

- **Останавливает бэкенд на несколько секунд** (согласованный снапшот SQLite в WAL-режиме —
  «на горячую» копировать нельзя). Перезапуск (`pm2 restart`) гарантирован даже при сбое (trap);
- при сбое tar **частичный архив удаляется** (не остаётся «почти полных» бэкапов);
- архивы на сервере: `<BACKUP_SERVER_DIR>` (по умолчанию `/var/backups/family`),
  имя `family-backup-<host>-<дата>.tar.gz`; **ротация** — хранятся последние `BACKUP_KEEP`
  (по умолчанию 7);
- при скачивании локально контрольная сумма sha256 сверяется с серверной (локально выводится
  `sha256:` и результат сверки).

---

## 3. Конфигурация

Читается из корневого `.env` (шаблон — `.env.example`; существующие переменные окружения не
переопределяются). Базовые параметры цели — как у деплоя:

| Переменная           | По умолчанию             | Назначение                                           |
| -------------------- | ------------------------ | ---------------------------------------------------- |
| `DEPLOY_HOST`        | `my.rybnikov.su`         | SSH-хост                                             |
| `DEPLOY_USER`        | `rybnikov`               | SSH-пользователь                                     |
| `DEPLOY_PORT`        | `22`                     | SSH-порт                                             |
| `DEPLOY_BACKEND_DIR` | `/var/www/<host>/server` | каталог бэкенда на сервере                           |
| `DEPLOY_PM2_APP`     | `family-backend`         | имя pm2-приложения                                   |
| `DEPLOY_PM2_HOME`    | `/home/rybnikov/.pm2`    | стабильный PM2_HOME (обязателен, см. docs/server.md) |

Специфичные для бэкапа:

| Переменная          | По умолчанию             | Назначение                                         |
| ------------------- | ------------------------ | -------------------------------------------------- |
| `BACKUP_SERVER_DIR` | `/var/backups/family`    | каталог архивов на сервере (создаётся через sudo)  |
| `BACKUP_LOCAL_DIR`  | `backups/` (корень репо) | локальная папка для скачивания (в git не попадает) |
| `BACKUP_KEEP`       | `7`                      | сколько последних архивов хранить на сервере       |
| `BACKUP_CRON_TIME`  | `0 3 * * *`              | расписание cron-бэкапа (время сервера)             |

## 4. Cron-бэкап

`npm run backup -- --install-cron` идемпотентно ставит на сервер автономный скрипт
`/home/rybnikov/.family-backup-cron.sh` и запись в crontab:

```
<BACKUP_CRON_TIME> /bin/bash /home/rybnikov/.family-backup-cron.sh >> <BACKUP_SERVER_DIR>/cron.log 2>&1
```

- Cron-скрипт самодостаточен (не зависит от локальной машины): остановка/снапшот/рестарт/ротация;
- лог — `<BACKUP_SERVER_DIR>/cron.log`;
- **ставится только на основном хосте** — данные живут там; тестовый хост — зеркало
  (правило 14 в AGENTS.md), его бэкапить не нужно.

## 5. Восстановление

```powershell
npm run restore -- <archive.tar.gz>                        # цель — DEPLOY_HOST / --host
npm run restore -- <archive.tar.gz> --host new.vps.example
npm run restore -- <archive.tar.gz> --no-env               # не восстанавливать .env (рабочий сохраняется)
npm run restore -- --from-server /var/backups/family/family-backup-....tar.gz
npm run restore -- <archive> --dry-run                     # показать план без сети
npm run restore -- <archive> --print-script                # показать remote-скрипт
npm run restore -- <archive> --skip-health                 # без health-check
```

Поведение:

- **Цель** — `--host` или `DEPLOY_HOST` (обязательно; дефолта нет, чтобы случайно не «восстановить»
  основной сервер). Каталог/имя приложения — через отдельное пространство **`RESTORE_*`**
  (`RESTORE_USER`, `RESTORE_PORT`, `RESTORE_BACKEND_DIR`, `RESTORE_PM2_APP`, `RESTORE_PM2_HOME`) —
  конфиг основного хоста из корневого `.env` (`DEPLOY_*`) к цели восстановления **не** применяется;
- **Страховка**: текущие `data/docs/images/.env` цели убираются в `/tmp/family-restore-prev-<дата>/`
  (не удаляются) — прежнее состояние всегда доступно для отката;
- **`.env`**: всегда сохраняется в страховку до распаковки (tar может его перезаписать архивным).
  По умолчанию восстанавливается `.env` из бэкапа; `--no-env` — восстанавливаются только
  `data/docs/images`, а рабочий `.env` цели возвращается на место (удобно при повторной
  синхронизации уже настроенного хоста);
- **рестарт** гарантирован (trap); после — health-check напрямую `127.0.0.1:<PORT>/api/health`
  (порт читается из `.env`, ожидание готовности до ~30 c; `.env` в CRLF корректно обрабатывается);
- `server-config/` и `MANIFEST.txt` из архива в каталог приложения **не** кладутся (убираются
  в страховку).

## 6. Восстановление на новый VPS (пошагово)

1. **Провижининг хоста** (вручную, чек-лист — подробно в `docs/server.md`):
   - пользователь с passwordless sudo, Node ≥ 22.5, nginx + letsencrypt (сертификат на **новый**
     домен), pm2 + systemd-автозапуск (`pm2-rybnikov.service`), python-venv для PDF-импорта;
   - каталог `/var/www/<host>/` с правами; конфиги nginx — из `server-config/` архива как образец
     (домен/пути/сертификаты — свои).
2. **Восстановление данных**:

   ```powershell
   npm run restore -- C:\backup\family-backup-my.rybnikov.su-20260821-030000.tar.gz --host new.vps.example
   ```

3. **Код**: `npm run deploy` с `DEPLOY_HOST`/`DEPLOY_BACKEND_DIR`/... на целевой хост (сборка +
   `node_modules` + рестарт).
4. **Проверка `server/.env`** на новом хосте: `PORT` (на обоих хостах — `3000`), `CORS_ORIGIN`
   (домен нового хоста), `RENOVATION_PYTHON` / `RENOVATION_EXTRACT_SCRIPT` (пути venv хостовые —
   при необходимости поправить и `pm2 restart`).

## 7. Подводные камни и гарантии

- **SQLite в WAL-режиме** — копировать только после остановки бэкенда (согласованный снапшот);
- **частичный архив при сбое** удаляется (не остаётся «почти полных» бэкапов, которые выглядели бы
  валидными);
- **`.env` цели никогда не теряется**: до распаковки сохраняется в `/tmp/family-restore-prev-*`;
- **`.env` в CRLF** (Windows) — health-check и чтение `PORT` корректно обрабатывают (`tr -d '\r'`);
- **sha256** сверяется при локальном скачивании бэкапа;
- **health-check после restore** — ожидание готовности до ~30 c (холодный старт Node + sharp +
  pdf.js может быть дольше пары секунд);
- **cron только на основном хосте** (правило 14 AGENTS.md).
