# Спецификация модуля «Ремонт» (renovation) — data-слой

| Поле          | Значение                                                                             |
| ------------- | ------------------------------------------------------------------------------------ |
| Тип документа | Модульная спецификация (Specification Driven Development)                            |
| Модуль        | Отчётность «Ремонта» в отдельной БД (`renovation.sqlite`); данные — через импорт PDF |
| Проект        | my.rybnikov.su — семейный портал (монорепозиторий: `frontend` + `backend`)           |

## 0. Контекст

Статичные страницы `projects/renovation/` содержали всю отчётность ремонта (смета, акты работ,
заказы материалов, взаиморасчёты, отчёты). Цель модуля — перенести эти данные в **отдельную БД
`data/renovation.sqlite`** и перевести просмотр и расчёт в приложение (React + Express).
Статичные HTML и старые навыки `project-renovation-*` теперь — только история (архив `projects/`
и `projects/skills-archive/`), приложение с ними не работает; наполнение БД — через импорт PDF
в приложении.

Текущий статус — **этапы 1–7 выполнены**: домен, отдельная БД, импорт PDF с верификацией;
read-API `/api/renovation/*`, страница приложения `#/projects/renovation` (сводка
«Работы»/«Материалы» + отчёты по ссылкам «Ход работ»/«Закупка материалов» (в модальном окне)), импорт PDF через `pdfplumber` (черновик → подтверждение), применение
доп. соглашений к смете (дифф → подтверждение → версионирование); карточка «Ремонт» в разделе
«Проекты» ведёт в приложение (`#/projects/renovation`), статичные страницы остаются архивом.
**Этап 7 (модалки вместо прямых ссылок):** «Дизайн-проект» и «Смета» на странице «Ремонт»
открывают модальные окна из БД/хранилища документов (документы дизайн-проекта — подпапка
`design/` каталога документов, смета/доп. соглашения — версии из БД со ссылками на исходные
PDF во встроенном просмотрщике); кнопка «Доп. соглашение» перенесена в модалку «Смета».
Прямые ссылки на статичные `estimates.html` и `pdf/...` с этой страницы убраны.

## 1. Требования

**FR-20. Отдельное хранилище отчётности «Ремонт».**

- 20.1 Данные ремонта живут в отдельной БД `data/renovation.sqlite` (путь — `RENOVATION_DB_PATH`,
  по умолчанию `data/renovation.sqlite` рядом с `backend/`). Это **не** `DB_PATH`
  (`data/vps.sqlite`) — базы разных модулей. Обе сохраняются при деплое (`server/data/`).
- 20.2 Наполнение — **штатное, через импорт PDF в приложении** (admin): `POST /api/renovation/pdf`
  → черновик → подтверждение; идемпотентность тип+дата → 409. Seed из статичных HTML убран
  (скрипт `seed-renovation.mjs` и команда `seed:renovation` удалены; первичные данные внесены
  исторически этим скриптом).
- 20.3 Денежные и количественные значения хранятся **целыми копейками (×100)**, каноническая
  логика — `backend/src/services/renovation/domain/money.ts` (`parseDecimal`, `parseKopecks`,
  `sumKopecks`, `overheadOf`, `formatKopecks`). Причина: REAL в SQLite неточен, а сверка
  «суммы сходятся» должна быть детерминированной.
- 20.4 Доменные модели — `backend/src/services/renovation/domain/types.ts` (чистые типы без
  зависимостей от Express/SQLite): версии сметы, позиции, документы (акты/заказы), ведомости.
- 20.5 Акты взаиморасчётов **кумулятивные**: в расчёт отчётности идёт только самый свежий на
  тип (по `date`), остальные — история (правило домена, не SQL).

## 2. Домен (типы)

- `EstimateVersion` — версия сметы: `kind` (`seed`/`current`/`history`/`addendum`), `date`,
  `label`, `total` (с накладными), `totalNoOverhead`, `overhead`, `addendumRef`,
  `sourcePath`, `pdfPath`, `items[]`.
- `EstimateItem` — позиция: `position`, `section`, `name`, `unit`, `price`, `qty`, `sum`
  (копейки), `change` (`none`/`changed`/`new`/`removed` — разметка по доп. соглашению;
  `removed` — позиция, удалённая при применении доп. соглашения, видна только в истории).
- `RenovationDoc` — акт работ (`work_act`) или заказ материалов (`material_order`): `number`,
  `date`, `title`, `total`, `overhead`, `totalWithOverhead`, `items[]`.
- `SettlementAct` — ведомость взаиморасчётов (`works`/`materials`): `rows[]` с `kind`
  (`row`/`subtotal`/`total`), `rowDate`, `reason`, `paidIn`, `used`, `balance`.
- `RenovationMeta` — реквизиты проекта (объект, договор, подрядчик, дата старта, срок, площадь).

## 3. Схема БД (`data/renovation.sqlite`)

Схема задана в `backend/src/db/renovationDatabase.ts` (блок `SCHEMA`, `CREATE TABLE IF NOT EXISTS`).
Таблицы:

- `renovation_meta` — реквизиты (одна строка, `id=1`).
- `estimate_versions` + `estimate_items` — версии сметы и позиции (снапшот на версию).
- `renovation_docs` + `renovation_doc_items` — акты работ и заказы материалов.
- `settlement_acts` + `settlement_rows` — ведомости взаиморасчётов.

Соглашения:

- Деньги/количество — INTEGER копеек (`qty` ×100). `NULL` — значение отсутствует («—»).
- `material_order`: `total` = итог заказа («Итого, с учетом накладных расходов»), `overhead` —
  вычисленная неявная накладная (итог − сумма позиций; 10% у заказов №1–№3, 0% у №4),
  `total_with_overhead` = NULL.
- `work_act`: `total` = «Итого по всем разделам», `overhead` = «Накладные расходы 5%»,
  `total_with_overhead` = grand-итог.
- `estimate_versions`: `total_no_overhead`/`overhead`/`total` из блока `doc-summary`; у
  доп. соглашений (`addendum`) — только `total` (= `total-big`).

## 4. Наполнение БД (штатное)

- Данные в `data/renovation.sqlite` ведутся **в приложении** — через импорт PDF (admin):
  `POST /api/renovation/pdf` (pdfplumber → черновик) → `POST /pdf/:id/confirm` (запись в БД);
  идемпотентность тип+дата → 409. Доп. соглашения применяются к смете через
  `POST /estimate/addendum/confirm` (версионирование). Ведомости взаиморасчётов — кумулятивные
  (правило 20.5).
- **Seed из статичных HTML убран**: скрипт `seed-renovation.mjs`, команда `seed:renovation`,
  переменная `RENOVATION_PROJECTS_DIR`, деплой-флаг `--seed-renovation` и каталог
  `server/renovation-source/` удалены. Повторная инициализация с нуля — только загрузкой PDF
  через приложение.

  сумма использования). Если в ведомости есть строка-подсумма «Подотчётные прораба»

  датой ≤ даты последней ведомости по типу), расходится со строкой «Учтено по актам»

  «Примечания» (`.renov-notes`) между карточками и вкладками собирает все сноски:
  «в т.ч. подотчётные прораба на сумму …» и «расхождение … между суммой по актам
  (заказам), учтённым в ведомости, и „Учтено по актам“ — соответствует исходным
  документам, не исправлено».

## 5.1. Импорт PDF (этап 3 — реализовано)

- **Парсер:** `pdfplumber` (Python) через subprocess — `backend/scripts/extract_pdf.py`
  (текст + таблицы, JSON в stdout, UTF-8 принудительно); адаптер —
  `services/renovation/import/pdfExtractor.ts` (интерпретатор/скрипт — `RENOVATION_PYTHON`/
  `RENOVATION_EXTRACT_SCRIPT`). **Кросс-платформенно:** дефолтный python — локальный venv с
  pdfplumber, путь зависит от ОС (Windows — `../.venv/Scripts/python.exe`, Debian/Ubuntu —
  `../.venv/bin/python`, иначе системный `python`/`python3`); на сервере путь задаётся явно
  через `RENOVATION_PYTHON` (см. `docs/server.md`).
- **Классификация** — `services/renovation/import/classify.ts`: тип по ключевым словам (заказ
  материалов / акт работ / ведомость / доп. соглашение), подтип ведомости (работы/материалы),
  дата (приоритет — из имени файла; для ведомостей — самая поздняя строка, кумулятивность),
  номер, заголовок. Номер документа — по «№N» либо латинской «N» («Заказ материалов N5 от …» —
  в шаблоне подрядчика встречается и такой вариант; без учёта «N» номер не извлекался и в UI
  показывался «—»).
- **Черновик** — `services/renovation/import/draft.ts`: разбор позиций/строк (таблицы pdfplumber,
  при их отсутствии — построчный текст: многострочные позиции, «Доставка/Подъём», «Всего»),
  итоги, `needsReview`/`warnings` при неполном разборе. Числовой хвост позиции «цена кол-во
  сумма» разбирается по токенам (`parseNumFields`), а не жадным regex с `[\d\s.,]+`: перебираются
  границы трёх полей, поэтому пробел-разделитель тысяч в сумме («735,00 153,00 112 455,00») не
  искажает её; выбирается вариант, где цена×кол-во = сумма. Переносы, попавшие внутрь позиции
  при извлечении текста (в том числе `2.` и дробная часть числа на следующей строке), склеиваются
  до разбора; текст после полной числовой строки добавляется к наименованию, а не к её сумме.
  Наименование многострочной
  позиции, идущее до числовой строки (после шапки таблицы), копится в `pending` и подставляется
  в позицию. Продолжение имени после числовой строки: строка без номера добавляется к имени
  последней позиции, если она идёт сразу после её строки-продолжения («толщиной до 25мм» после
  «3 м2+м.п. 580.00 …»). Если же строка без номера стоит после ПОЛНОЙ однострочной позиции
  (номер+имя+цифры на одной строке — её имя уже целиком) либо после имени другой позиции и за
  ней идёт числовая строка — это начало имени следующей позиции: в PDF подрядчика номер
  печатается на строке с цифрами, а имя переносится перед ней («2 Установка маяков…» →
  «Оштукатуривание…» → «3 м2+м.п. …»). Такая строка накапливается в `pending` и не склеивается
  с предыдущим именем. Подвал «Страница: N / M» и метки «[стр. N]» НЕ прерывают разбор
  (в многостраничных PDF позиции продолжаются на следующих страницах); концом документа
  считается блок «Подписи сторон». Позициям присваивается раздел документа: строка «Раздел N. …» (в тексте — отдельной
  строкой, в таблицах — строкой в колонке наименования) становится разделом следующих позиций
  (`DraftItem.section`; при подтверждении — колонка `section` документа, см. §5.3 «Ход работ»).
  Проза акта не попадает в позиции: нумерованные строки до шапки таблицы («1. Подрядчик
  выполнил…») и после «Итого…» («2. Всего выполнено работ…») пропускаются, строка «Накладные
  расходы…» — тоже; после «Итого» нечисловые строки к позициям не добавляются (новый «Раздел N»
  после итога сбрасывает это правило — дальше снова могут идти позиции). Черновики живут в
  памяти (`draftStore.ts`, TTL 30 мин).
- **Эндпоинты** (admin, см. `docs/specification-api.md` §2.5):
  - `POST /api/renovation/pdf` (multipart) — извлечение + классификация → `{ draft }`;
  - `POST /api/renovation/pdf/:id/confirm` — идемпотентность (тип+дата → 409) → запись в БД.
- **Фронтенд:** модалка `RenovationPdfModal.tsx` (admin, кнопка «Импорт PDF» на странице
  «Ремонт»): выбор PDF → загрузка → предпросмотр черновика (тип/дата/позиции/итог/предупреждения)

### 5.1.1. Сохранение загруженных PDF и просмотр в приложении

- **Хранение:** загруженный PDF при подтверждении импорта сохраняется в
  `RENOVATION_DOCS_DIR` (по умолчанию `docs/renovation` относительно CWD бэкенда: dev —
  `backend/docs/renovation`, сервер — `server/docs/renovation`, каталог **сохраняется** при
  деплое, как `data/`). Сервис — `services/renovation/import/pdfStore.ts`:
  - при загрузке (`POST /pdf`) файл кладётся как pending (`docs/.pending/<draftId>.pdf`) и
    переносится в каталог документов при подтверждении (`finalizePdf`);
  - имя файла — детерминированное по классификации (`pdfFileName`):
    `settlement_<works|materials>_<дата>.pdf`, `work_act_<дата>[_<номер>].pdf`,
    `material_order_<дата>[_<номер>].pdf`, `addendum_<дата>.pdf`;
  - осиротевшие pending-файлы вычищаются по TTL (`cleanupPendingPdfs`), при ошибке сохранения
    перенесённый файл удаляется (`discardPdf`).
- **Раздача:** `GET /api/renovation/docs/:file` (под `requireAuth`) отдаёт PDF из каталога
  документов; имя проверяется (только `[a-z0-9._-]`, без выхода за каталог — path traversal),
  400 — некорректное имя, 404 — файл не найден. В БД пишется `pdf_path` =
  `/api/renovation/docs/<file>` (заполняется при подтверждении: `insertRenovationDoc`,
  `insertSettlementAct`, `insertAddendumVersion`).
- **`pdf_path` у записей:** URL приложения `/api/renovation/docs/<file>` у всех записей —
  импортированных и из seed (PDF лежат в `server/docs/renovation/`, включая перенесённые
  со статичного архива). Просмотрщик умеет и «прямые» серверные пути (`/projects/...`) —
  как fallback, в БД таких значений уже нет.
- **Перенос существующих PDF (выполнен и на сервере, и в dev):** файлы, на которые ссылался
  seed через статичный архив (`public_html/projects/renovation/pdf/…`), перенесены в
  `server/docs/renovation/` с именами по тем же правилам (акты/заказы/ведомости —
  `pdfFileName`, смета — `estimate.pdf`, доп. соглашения — `addendum_<дата>_<id>.pdf`), а
  `pdf_path` в БД переписан на `/api/renovation/docs/<file>` (все таблицы: `estimate_versions`,
  `renovation_docs`, `settlement_acts`). Статичный архив `public_html/projects/` на сервере удалён;
  оставшиеся PDF и фотографии сохранены в `server/docs/renovation/legacy/`.
- **Документы дизайн-проекта** — подпапка `design/` каталога документов
  (`docs/renovation/design/`; имена файлов — безопасные `[a-z0-9._-]`, человекочитаемые
  заголовки — карта `DESIGN_TITLES` в `pdfStore.ts`). Список — `GET /api/renovation/design`
  (`{ docs: { fileName, title, url }[] }`, по заголовку), раздача —
  `GET /api/renovation/docs/design/:file` (под `requireAuth`, path traversal-защита как у
  плоских файлов). Кнопка «Дизайн-проект» на странице «Ремонт» открывает модалку со списком
  (`RenovationDesignModal.tsx`), по клику на документ — встроенный просмотрщик `PdfViewerModal`.
  Для документов дизайн-проекта просмотрщик открывается с `fitToWidth`: форма растягивается так,
  чтобы самая широкая страница помещалась целиком по ширине (без горизонтальной прокрутки), но
  не шире доступного экрана; остальные PDF (смета, акты, отчёты) — с дефолтной шириной.
- **Просмотр:** фронтенд-компонент `components/PdfViewerModal.tsx` (pdf.js / `pdfjs-dist`,
  ленивый чанк): скачивает файл через `fetchFileBytes` (`api/client.ts`; для `/api/*` — с
  обработкой 401), рисует страницы на `<canvas>` с листанием, масштабом и индикатором страницы.
  Ссылки-кнопки на исходные PDF (с иконкой документа, примитив `PdfLink`): в «Блоке 2.
  Материалы» сводки (`RenovationPage.tsx`) и в шапках заказов отчёта «Материалы»

## 5.2. Применение доп. соглашений к смете (этап 4 — реализовано)

**Проблема.** Импортированные доп. соглашения (`estimate_versions` с `kind='addendum'`) хранят
только свои позиции и итог, но не «встроены» в актуальную смету. Нужно применить соглашение к
`current` с пересчётом итогов и сохранением версии до применения (для аудита/отката).

**Движок диффа** — `services/renovation/addendum.ts` (чистая логика, без Express/SQLite):

- `normalizeName(name)` — нижний регистр, пунктуация `|,.;:()«»"'`/\\` → пробел, схлопывание
  пробелов, слова «толщиной»/«слоем» (размерные уточнения толщины слоя) игнорируются —
  «…толщиной до 25мм» ≡ «…до 25мм». Ключ сопоставления позиций.
- `targetSection(section)` — секция «…— дополнительные работы» → базовая («Раздел 5. Электрика
  — дополнительные работы» → «Раздел 5. Электрика»).
- `buildAddendumProposal(current, addendum)` → `{ diffs, newTotal…, needsReview, warnings }`:
  позиции соглашения сопоставляются с `current` по `normalizeName` — точное совпадение →
  `update` (изменение), отсутствие → `new` (добавление); позиции `current`, не затронутые
  соглашением, → `keep` (сохраняются по умолчанию; пользователь может пометить на удаление).
  Пустое наименование позиции → warning.
- `newItemsAfter(current, addendum, removeKeys)` — позиции после применения: `current` в исходном
  порядке, совпавшие — значениями из соглашения (`change='changed'`); новые позиции соглашения
  вставляются в конец своей секции (`change='new'`); **помеченные на удаление не возвращаются**
  (фильтр в шаге добавления новых); сквозная перенумерация 1..N.
- `historyItemsAfter(current, removeKeys)` — историческая копия старой `current`: удалённые
  позиции помечаются `change='removed'`.
- `totalsAfter(current, addendum, removeKeys)` — пересчёт: сумма позиций → «Итого по всем
  разделам» + накладные 5% = «Итого» (`OVERHEAD_PERCENT = 5`).

**Версионирование** — `db/renovationRepository.ts::applyAddendumVersion` (транзакция):

1. старая `current` → `kind='history'`, `date = дата доп. соглашения`,
   `label = "<старый> (до доп. соглашения <label>)"`, позиции — из `historyItemsAfter`;
2. создаётся новая `current` (`date=NULL`, итоги из `totalsAfter`, `addendum_ref = label`
   соглашения), позиции — из `newItemsAfter`.

**Эндпоинты** (admin, `routes/renovation.ts`, детали — `docs/specification-api.md` §2.5):

- `POST /api/renovation/estimate/addendum` — тело `{ addendumId }` → `{ proposal }` (дифф +
  новый итог), без записи;
- `POST /api/renovation/estimate/addendum/confirm` — тело `{ addendumId, removeKeys?: string[] }`
  → применяет и возвращает `{ currentId, total, totalNoOverhead, overhead, itemsCount }` (201).
  Проверки: `addendumId`/`addendum.kind='addendum'`, у соглашения есть `date`, есть `current`.

**Фронтенд:** модалка `AddendumModal.tsx` (admin, кнопка «Доп. соглашение» — в модалке
«Смета», `RenovationEstimateModal.tsx`; открывается поверх неё, Escape закрывает только её):
список соглашений (`GET /estimate/versions`) → выбор → дифф (Было/Стало, метки
изменение/добавление/без изменений) → чекбоксы «Удалить» для позиций `keep` → итоги
(Итого по всем разделам / Накладные 5% / Итого) → «Применить доп. соглашение» → перезагрузка
сводки. API-клиент: `fetchRenovationEstimateVersions`, `fetchRenovationAddendumProposal`,
`confirmRenovationAddendum` (`api/client.ts`).

**Проверено (curl + браузер):** proposal по соглашению №2 — 8 изменений + 54 без изменений,
итог без изменений (соглашение уже встроено в `current`); confirm — старая `current` → `history`
с датой соглашения, новая `current` (#97/#113), удаление позиции «Укладка демпферной ленты»
(10 477,74 ₽) → 61 поз., итог 2 029 008,85 ₽ (пересчёт с накладными 5% сходится).

## 5.3. Отчёты из БД (этап 5 — реализовано)

Замена статичных `Reports/report_work.html` и `Reports/report_materials.html`: отчёты строятся
из БД на лету, без ручной/LLM-сборки HTML.

- **«Ход работ»** — `services/renovation/reports.ts::buildWorkReport()` + `GET /api/renovation/reports/work`:
  план = позиции актуальной сметы (`current`), факт = позиции актов работ. Ключ сопоставления —
  нормализованный «раздел::имя» (`normalizeName(section) + normalizeName(name)`): одинаковые
  имена в разных разделах (напр. «Укладка керамогранита…» в «Полах» и «Стенах») — разные
  позиции. Для уникального имени факт = сумма по всем актам; для ДУБЛИКАТОВ имён в одном
  разделе (в смете «Грунтование стен/откосов…» и «Установка маяков для штукатурки» встречаются
  дважды) факты распределяются по порядку: i-я позиция сметы берёт i-й факт (по порядку актов
  и позиций), «лишние» факты сверх числа дубликатов — в `added`. Каждая строка: план (цена/объём/сумма), факт
  (объём/сумма), статус
  (`done` — есть факт и отклонение 0; `partial` — есть факт, но отклонение ≠ 0; `notdone` — факта
  нет; `added` — в акте есть строка, которой нет в смете; она добавляется в **свой раздел акта**
  (раздел, извлечённый при импорте из «Раздел N. …», при отсутствии — «Прочее») и отмечается
  синим кружком в легенде); отклонение `факт − план` (`diff`) на бэкенде определяет
  статус и отдельной колонкой в UI не выводится. Секции сохраняют порядок сметы; `asOf` —
  самая поздняя дата документа; сводка взаиморасчётов по работам (последний акт, кумулятивность).
  Итоги шапки (план/факт/освоение %) — **с накладными**, как в сводке карточки «Работы»
  (`planSum` = `total` актуальной сметы, `factSum` = сумма `totalWithOverhead` актов);
  позиции строк — без накладных (накладные не привязаны к отдельным строкам). Счётчики статусов —
  по строкам отчёта.
- **«Материалы»** — `buildMaterialsReport()` + `GET /api/renovation/reports/materials`: заказы
  материалов с позициями и итогами (в т.ч. накладные), сводка (кол-во заказов, итого закуплено,
  итого накладных).
- **Фронтенд:** на странице «Ремонт» — ссылки «Ход работ» / «Закупка материалов» в карточках
  «Работы»/«Материалы», отчёты открываются в модальном окне
  (`components/Modal.tsx`, `modal--report`) (`RenovationPage.tsx`, ленивая загрузка
  через `hooks/useRenovationReports.ts` с кэшем);
  компоненты `components/RenovationWorkReport.tsx`, `components/RenovationMaterialsReport.tsx`;
  типы и функции — `api/client.ts` (`fetchRenovationWorkReport`, `fetchRenovationMaterialsReport`).
  Таблица «Ход работ» (`renov-rp__table--fixed renov-rp__table--work`): колонки — статус
  (иконка-точка, подпись — в тултипе, расшифровка — в легенде; иконка прижата к правому краю
  колонки — ближе к наименованию) | наименование (pill единицы измерения прижат к правому краю,
  flex `.renov-rp__name`) | цена | объём (план/факт) | сумма (план/факт); колонок «№» и
  «Отклонение» нет. Заголовок в 2 ряда: «Наименование работ» объединяет колонки
  статус+наименование (`rowSpan=2 colSpan=2`), «Цена» — по высоте 2 рядов, «Объём» и «Сумма»
  объединяют по 2 колонки «план»/«факт». В строке-заголовке каждой группы (`renov-rp__section`)
  — подитог группы: малый pill «выполнено строк N / M» (done+partial из общего числа строк
  группы; `.renov-pill--sm`) справа в колонке наименования (flex `.renov-rp__section-title`),
  малый pill «% выполнения по объёму» (сумма объёмов факт / план × 100) под колонкой
  «Объём-план» и суммы план/факт под колонками «Сумма». В шапке отчёта вместо
  текстового «План/Факт/Освоение» — прогресс-бар освоения как в карточке «Работы»
  (`.renov-card__progress`, «факт из план» + %); дата отчёта (`asOf`) — pill-тегом в заголовке
  модалки после «Отчет о ходе работ» (`renov-pill`, `Modal.title` принимает ReactNode). Легенда — только
  статусы (без «перерасход/экономия»). Ширины колонок (кроме наименования) фиксированы
  (`table-layout: fixed` + `colgroup`, `.renov-rp__col-*`), шрифт таблицы меньше (`0.75rem`) —
  значения не наезжают.
  Таблица «Материалы» в каждом заказе (`renov-rp__table--fixed renov-rp__table--materials`) —
  тот же стиль отчётной таблицы: колонки № | наименование | цена | кол-во | сумма (колонки
  «Ед.» нет — единица измерения pill-тегом справа в колонке наименования, как в «Ход работ»);
  столбец «№» во всех заказах одинаковой ширины (`renov-rp__col-num`).
- **Ограничение автоматики:** сопоставление план↔факт — по нормализованному «раздел::имя»
  (игнорируются «толщиной»/«слоем»). Дубликаты имён в разделе распределяются позиционно (по
  порядку); при расхождении порядка строк акта и сметы возможна неточная привязка факта к
  дубликату. Существенно разные формулировки (вне игнорируемых слов) по-прежнему не
  «склеиваются» (строка — «не выполнено» / добавлена как новая). При необходимости — словарь
  синонимов/ручное сопоставление.

## 7. Решения и находки (ADR + факты из данных)

Общие ADR — в `docs/specification.md` (§12, ADR-13…ADR-18). Здесь — факты о данных проекта и
грабли, зафиксированные при импорте:

- **Копейки (×100).** REAL в SQLite неточен; сверка «суммы сходятся» и пересчёт накладных должны
  быть детерминированными. Канон — `domain/money.ts` (используется импортом PDF, отчётами и
  доп. соглашениями).
- **Оба десятичных разделителя.** В PDF/HTML встречаются и запятая (`141 127,88`), и точка
  (`134 407.50`); разделитель тысяч — пробел/неразрывный пробел. Нормализация — в `parseDecimal`.
- **Минус — U+2212 (`−`), не ASCII.** В PDF/HTML отрицательные суммы записаны символом U+2212
  (`−22 832,80`); `parseDecimal` приводит его к ASCII `-` перед разбором.
- **Отрицательные десятичные.** `parseDecimal` трактует знак как знак модуля:
  `−22 832,80` → `-(22832 + 0.80)`, а не `-22832 + 0.80` (иначе получалось `-22 831,20`).
- **Знак «Подотчетные прораба» непоследователен.** В ведомости 17.07 — `+50 000,00`,
  в 06.08 — `−50 000,00`; оба уменьшают баланс на 50 000. Верификация не зависит от знака
  (строки-подсуммы пропускаются; строка «Всего» проверяется по собственной арифметике
  `внесено − использовано = баланс`).
- **Неявные накладные в заказах материалов.** Итог «с учетом накладных расходов» не содержит
  отдельной строки накладных: `накладные = итог − сумма позиций` (10% у заказов №1–№3, 0% у №4).
  Сохраняется вычисленное значение; верификация допускает ровно 0% или 10%.
- **«Доставка»/«Подъём» — позиции заказа.** В заказах материалов это обычные строки таблицы
  (без цены/количества), сохраняются как позиции.
- **Кумулятивные ведомости.** В расчёт отчётности идёт только последний акт на тип (по `date`).
  Строка-подсумма «Подотчетные прораба» имеет только баланс и уменьшает накопленный баланс
  (учтено в верификации).
- **Два варианта разметки секций.** В смете секции — `<div class="section">`; в актах и доп.
  соглашениях — обычный `<div>` + `.section-title`. Парсер `parseTablesWithSections` находит
  таблицы и назначает им ближайший предшествующий `section-title`. Шапки таблиц (`<th>`) в данные
  не идут.
- **Наполнение — только через приложение.** Источник истины — БД `data/renovation.sqlite`;
  новые данные попадают в неё только через импорт PDF (`pdfplumber`, `POST /api/renovation/pdf`).
  HTML-парсинг из статичного архива (seed) удалён вместе со скриптом `seed-renovation.mjs`.
- **Репозиторий и схема.** `db/renovationDatabase.ts`/`db/renovationRepository.ts` — схема задана
  в `db/renovationDatabase.ts` (единый источник, блок `SCHEMA`).
- **Prettier на Windows.** `npm run format` = `prettier --write .` переписывает все файлы CRLF→LF,
  создавая шум в `git status` (M без содержательных изменений). Форматировать только изменяемые
  файлы. `.prettierignore` исключает `.venv/`, `dist/`, `node_modules/`, `temp/` (иначе локальный
  Python-venv ломает запуск format).
- **id строк в серверной БД ≠ локальные.** Автоинкремент на сервере не совпадает с локальным
  (напр. доп. соглашение №2 — локально id=123, на сервере id=11). При операционной правке данных
  «Ремонта» прямо на сервере искать строку по `label`/`pdf_path`/тип+дата, а НЕ по id.
- **Исправление некорректно импортированных данных на сервере.** Переимпорт уже
  импортированного документа блокируется идемпотентностью (тип+дата → 409), delete-эндпоинта для
  документов нет → исправление — только прямым UPDATE в `server/data/renovation.sqlite`
  (`renovation_docs`, `renovation_doc_items`, `estimate_versions`); при переименовании файла PDF
  править и `pdf_path` (`/api/renovation/docs/<file>`, имя — безопасное `[a-z0-9._-]`).
- **`resolveScript`/`resolvePython` (грабля `??` на пустой строке).** Дефолт
  `RENOVATION_EXTRACT_SCRIPT` — пустая строка; `??` на пустой строке не срабатывает (в отличие от
  `||`) → python получает пустой путь и падает («can't find '**main**' module in '<cwd>'»).
  Использовать `||`.
- **Дата доп. соглашения в seed (этап 4).** `dateFromEstimateName` долго не обрабатывал префикс
  `estimate_add_` — дата аддендумов оставалась `NULL` (а для версионирования «до доп.
  соглашения» дата обязательна). Исправлено: `/estimate_(?:add_)?(\d{4}-\d{2}-\d{2})/`.
- **Помеченные на удаление не должны возвращаться (этап 4).** В первой версии `newItemsAfter`
  позиция, удалённая `removeKeys` и присутствующая в доп. соглашении, заново добавлялась в шаге
  «новые позиции» (итог не менялся). Исправлено: шаг добавления новых фильтрует `removeKeys`.
- **Дубликаты нормализованных имён.** В смете есть повторяющиеся наименования
  («Грунтование стен/откосов перед оштукатуриванием» — поз. 17 и 21, секция «Стены»; то же для
  «Установка маяков…»; «Укладка керамогранита…» и «Затирка швов…» дублируются по имени, но в
  разных разделах). В отчёте «Ход работ» дубликаты учитываются: ключ «раздел::имя», факты для
  дубликатов в одном разделе распределяются позиционно (i-я позиция — i-й факт; лишние факты —
  «added»). В диффе доп. соглашений сопоставление по имени (Map) — последнее совпадение
  без изменений; в UI-таблице диффа ключи строк — по индексу, чтобы не было дублей React-ключей.
- **Версионирование транзакцией.** `applyAddendumVersion` выполняет UPDATE старой `current` +
  перезапись её позиций + INSERT новой `current` + позиций в одном BEGIN/COMMIT (ROLLBACK при
  ошибке) — старое и новое состояние никогда не видны «наполовину».

## 8. Устаревший статичный поток (история)

Раньше «Ремонт» вёл отчётность как **статичные HTML** (`projects/renovation/`): PDF распознавался
вручную/навыком `project-renovation-update-from-pdf` в HTML-документ (смета, акты, заказы,
ведомости), затем навык `project-renovation-build-reports` строил HTML-отчёты. Этот поток
**упразднён**; его роль полностью выполняет приложение:

- **Разбор PDF** → `services/renovation/import/*` (`pdfExtractor`, `classify`, `draft`, `draftStore`)
  через `POST /api/renovation/pdf` (тип по ключевым словам, дата из имени/строк, черновик).
- **Классификация документов** (акт работ / заказ материалов / ведомость / доп. соглашение) —
  `services/renovation/import/classify.ts`.
- **Отчётность** (план vs факт, материалы, взаиморасчёты) — `services/renovation/reports.ts`
  (`buildWorkReport`, `buildMaterialsReport`) и `services/renovation/overview.ts` (сводка).
- **Доп. соглашения** — `services/renovation/addendum.ts` (дифф по `normalizeName`, версионирование).
- **Деньги/количество** — `domain/money.ts` (копейки ×100); доменные правила (кумулятивные
  ведомости, разметка версий) — разделы 1–2.

Архивные артефакты (только история, не использовать): статичные HTML `projects/renovation/`,
общие ассеты `projects/styles.css`/`theme.js`/`icon-sprite.svg`, навыки `project-renovation-*`
(`projects/skills-archive/`). На сервере статичный архив `public_html/projects/` удалён; оставшиеся
PDF и фотографии — в `server/docs/renovation/legacy/`.
