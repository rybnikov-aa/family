# Спецификация модуля «Ремонт» (renovation) — data-слой

| Поле          | Значение                                                                       |
| ------------- | ------------------------------------------------------------------------------ |
| Тип документа | Модульная спецификация (Specification Driven Development)                      |
| Модуль        | Отчётность проекта «Ремонт» (`projects/renovation/`) → данные в SQLite         |
| Проект        | family.rybnikov.su — семейный портал (монорепозиторий: `frontend` + `backend`) |

## 0. Контекст

Статичные страницы `projects/renovation/` содержат всю отчётность ремонта (смета, акты работ,
заказы материалов, взаиморасчёты, отчёты). Их «логика» сейчас живёт в HTML-файлах как данных и в
навыках-промптах (`.github/skills/project-renovation-update-from-pdf`,
`project-renovation-build-reports`). Цель модуля — перенести эти данные в **отдельную БД
`data/renovation.sqlite`** и, далее (этапы 2+), перевести просмотр и расчёт в приложение
(React + Express). Статичные страницы при этом остаются read-only архивом.

Текущий статус — **этапы 1–6 выполнены**: домен, отдельная БД, seed-импорт с верификацией;
read-API `/api/renovation/*`, страница приложения `#/projects/renovation` (сводка
«Работы»/«Материалы» + отчёты по ссылкам «Ход работ»/«Закупка материалов» (в модальном окне)), импорт PDF через `pdfplumber` (черновик → подтверждение), применение
доп. соглашений к смете (дифф → подтверждение → версионирование); карточка «Ремонт» в разделе
«Проекты» ведёт в приложение (`#/projects/renovation`), статичные страницы остаются архивом.

## 1. Требования

**FR-20. Отдельное хранилище отчётности «Ремонт».**

- 20.1 Данные ремонта живут в отдельной БД `data/renovation.sqlite` (путь — `RENOVATION_DB_PATH`,
  по умолчанию `data/renovation.sqlite` рядом с `backend/`). Это **не** `DB_PATH`
  (`data/vps.sqlite`) — базы разных модулей. Обе сохраняются при деплое (`server/data/`).
- 20.2 Первичное наполнение — из статичных HTML `projects/renovation/` скриптом
  `npm run seed:renovation -w backend` (`backend/scripts/seed-renovation.mjs`). Скрипт
  идемпотентен (очищает таблицы модуля и наполняет заново) и **верифицирует** импорт:
  суммы позиций сходятся с итогами документов, пораздельные итоги сметы — с
  «Итого по всем разделам», накопленный баланс ведомостей — с итогом.
- 20.3 Денежные и количественные значения хранятся **целыми копейками (×100)**, каноническая
  логика — `backend/src/services/renovation/domain/money.ts` (`parseDecimal`, `parseKopecks`,
  `sumKopecks`, `overheadOf`, `formatKopecks`). Причина: REAL в SQLite неточен, а сверка
  «суммы сходятся» должна быть детерминированной.
- 20.4 Доменные модели — `backend/src/services/renovation/domain/types.ts` (чистые типы без
  зависимостей от Express/SQLite): версии сметы, позиции, документы (акты/заказы), ведомости.
- 20.5 Акты взаиморасчётов **кумулятивные**: в расчёт отчётности идёт только самый свежий на
  тип (по `date`), остальные — история (правило домена, не SQL).

## 2. Домен (типы)

- `EstimateVersion` — версия сметы: `kind` (`seed`/`current`/`history`/`addendum`), `date`,
  `label`, `total` (с накладными), `totalNoOverhead`, `overhead`, `addendumRef`,
  `sourcePath`, `pdfPath`, `items[]`.
- `EstimateItem` — позиция: `position`, `section`, `name`, `unit`, `price`, `qty`, `sum`
  (копейки), `change` (`none`/`changed`/`new`/`removed` — разметка по доп. соглашению;
  `removed` — позиция, удалённая при применении доп. соглашения, видна только в истории).
- `RenovationDoc` — акт работ (`work_act`) или заказ материалов (`material_order`): `number`,
  `date`, `title`, `total`, `overhead`, `totalWithOverhead`, `items[]`.
- `SettlementAct` — ведомость взаиморасчётов (`works`/`materials`): `rows[]` с `kind`
  (`row`/`subtotal`/`total`), `rowDate`, `reason`, `paidIn`, `used`, `balance`.
- `RenovationMeta` — реквизиты проекта (объект, договор, подрядчик, дата старта, срок, площадь).

## 3. Схема БД (`data/renovation.sqlite`)

Схема задана в `backend/scripts/seed-renovation.mjs` (блок `SCHEMA`, `CREATE TABLE IF NOT EXISTS`)
и является источником для `db/renovationDatabase.ts` на этапе API. Таблицы:

- `renovation_meta` — реквизиты (одна строка, `id=1`).
- `estimate_versions` + `estimate_items` — версии сметы и позиции (снапшот на версию).
- `renovation_docs` + `renovation_doc_items` — акты работ и заказы материалов.
- `settlement_acts` + `settlement_rows` — ведомости взаиморасчётов.

Соглашения:

- Деньги/количество — INTEGER копеек (`qty` ×100). `NULL` — значение отсутствует («—»).
- `material_order`: `total` = итог заказа («Итого, с учетом накладных расходов»), `overhead` —
  вычисленная неявная накладная (итог − сумма позиций; 10% у заказов №1–№3, 0% у №4),
  `total_with_overhead` = NULL.
- `work_act`: `total` = «Итого по всем разделам», `overhead` = «Накладные расходы 5%»,
  `total_with_overhead` = grand-итог.
- `estimate_versions`: `total_no_overhead`/`overhead`/`total` из блока `doc-summary`; у
  доп. соглашений (`addendum`) — только `total` (= `total-big`).

## 4. Seed-импорт

- Скрипт: `backend/scripts/seed-renovation.mjs` (ESM, `node:sqlite`, без сборки — как
  `scripts/users.mjs`). Запуск: `npm run seed:renovation -w backend` (или
  `node scripts/seed-renovation.mjs` из `backend/`).
- Источник: `RENOVATION_PROJECTS_DIR` (по умолчанию `../projects/renovation` относительно
  `backend/`). Обрабатываются: `estimate*.html` (кроме `estimates.html` — навигация),
  `Works/*.html`, `Materials/*.html` (акты/заказы/ведомости).
- Классификация файлов: `estimate_seed` → seed; `estimate_add_*` → addendum; `estimate_*` →
  history; `estimate.html` → current; `Works/act_*_settlement.html` → ведомость по работам;
  `Materials/report_*_settlement.html` → ведомость по материалам; `Works/act_*.html` →
  work_act; `Materials/report_*.html` → material_order.
- Парсинг HTML — регулярками по регулярной разметке документов (секции `.section`/`.section-title`,
  классы колонок `col-*`, блоки `doc-summary`, `totals-block`, `doc-sources`); шапки таблиц
  (`<th>`) пропускаются.
- **Верификация** (встроена в скрипт, печатает ✓/✗ по каждому файлу):
  - смета: сумма позиций раздела = итог раздела; сумма всех позиций = «Итого по всем разделам»;
    «Итого по всем разделам» + накладные = «Итого»; grand = «Итого»;
  - акт работ: сумма позиций = «Итого по всем разделам»; итого + накладные = итого с накладными;
  - заказ материалов: накладная = итог − сумма позиций; ожидаемая накладная — 0% или ровно 10%
    (иначе — предупреждение на ручную проверку);
  - ведомость: накопленный баланс строк = балансу каждой строки и строке «Всего»
    (строка-подсумма «Подотчетные прораба» уменьшает баланс).

  сохранения сводка перезагружается.
- **Шапка карточки «Работы»:** вместо строк «Смета (план)»/«Выполнено по актам» и бейджа
  процента — прогресс-бар освоения бюджета под заголовком (`components/RenovationSummaryCard.tsx`,
  проп `progress` = факт по актам из плана сметы, CSS `.renov-card__progress-*`): заливка —
  факт/план (ширина 0–100%, % может быть >100 при перерасходе), подпись «факт из план» + %.
- **Бюджет на материалы («Материалы»):** прогресс-бар как у карточки «Работы» —
  подпись «сумма по заказам из бюджета на материалы» + %, где сумма бюджета — ссылка (admin),
  открывает форму `components/MaterialsBudgetModal.tsx` (способ задания: % от сметы на работы,
  по умолчанию 100%, либо явная сумма); строка «Итого заказы материалов» не выводится (итог
  виден в подписи прогресс-бара). Настройка хранится в `renovation_settings` (`materials_budget`,
  JSON `{mode, percent, amount}`); сервис `services/renovation/budget.ts` —
  `getMaterialsBudgetSetting`/`getMaterialsBudget`/`updateMaterialsBudget`. Действующий бюджет
  (`value`, копейки): в режиме `percent` — `percent`% от актуальной `current`-сметы
  (пересчитывается на лету при изменении сметы), в режиме `amount` — явная сумма.
  API: `PUT /api/renovation/materials-budget` (admin); в сводке — поле `materialsBudget`.
- **Строки документов в сводке** (акты в «Блоке 1. Работы», заказы в «Блоке 2. Материалы») —
  компонент `components/RenovDocRow.tsx`: четыре столбца «дата | № (ссылка на PDF) | сумма |
  статус» (CSS `.renov-doc-row` в `styles/renovation.css`); суммы выровнены вправо, статус — в
  конце строки (`.renov-doc-status` фиксированной ширины для ровного выравнивания сумм).
  Статус — учёт в ведомости взаиморасчётов: если дата документа ≤ даты последней ведомости
  (по типу), зелёная галочка (`.renov-doc-check`), иначе жёлтая точка (`.renov-doc-dot`);
  при «не учтён» сумма строки приглушается (`.renov-doc-value--dim`).
  Номера актов — из БД `number`, при отсутствии (null) — порядковый номер в списке
  («Акт №1»). Счётчик документов в заголовке — pill-тег (`.renov-pill`) сразу после текста
  заголовка, как pill даты ведомости; в ссылках «Ход работ»/«Закупка материалов» счётчик
  показывает «N акт/акта/актов» и «N отчет/отчета/отчетов» (склонение — `utils/plural.ts`). Заголовки «Взаиморасчёты (работы)/(материалы)» —
  ссылки на PDF ведомости (`pdfPath` из сводки, компонент `components/RenovationSettlement.tsx`);
  дата ведомости — pill-тегом после заголовка (без «от»). Взаиморасчёты (работы и
  материалы): подписи «Внесено заказчиком» / «Учтено по актам» / «Учтено всего» /
  «Остаток». Строка «Учтено» всегда делится на две: «Учтено по актам» (использовано
  минус подотчётные, при их отсутствии — равно итогу) и «Учтено всего» (итоговая
  сумма использования). Если в ведомости есть строка-подсумма «Подотчётные прораба»
  (`foremenAmount` в сводке), к подписи «Учтено всего» добавляется сноска
  (`.renov-note-ref`). Если сумма документов, учтённых в ведомости (акты/заказы с
  датой ≤ даты последней ведомости по типу), расходится со строкой «Учтено по актам»
  (в т.ч. на копейки), к «Учтено по актам» добавляется сноска о расхождении. Блок
  «Примечания» (`.renov-notes`) между карточками и вкладками собирает все сноски:
  «в т.ч. подотчётные прораба на сумму …» и «расхождение … между суммой по актам
  (заказам), учтённым в ведомости, и „Учтено по актам“ — соответствует исходным
  документам, не исправлено».
- Остаётся: `POST /api/renovation/estimate/addendum` — этап 4; `GET /api/renovation/reports/*` — этап 5.

## 5.1. Импорт PDF (этап 3 — реализовано)

- **Парсер:** `pdfplumber` (Python) через subprocess — `backend/scripts/extract_pdf.py`
  (текст + таблицы, JSON в stdout, UTF-8 принудительно); адаптер —
  `services/renovation/import/pdfExtractor.ts` (интерпретатор/скрипт — `RENOVATION_PYTHON`/
  `RENOVATION_EXTRACT_SCRIPT`). **Кросс-платформенно:** дефолтный python — локальный venv с
  pdfplumber, путь зависит от ОС (Windows — `../.venv/Scripts/python.exe`, Debian/Ubuntu —
  `../.venv/bin/python`, иначе системный `python`/`python3`); на сервере путь задаётся явно
  через `RENOVATION_PYTHON` (см. `docs/server.md`).
- **Классификация** — `services/renovation/import/classify.ts`: тип по ключевым словам (заказ
  материалов / акт работ / ведомость / доп. соглашение), подтип ведомости (работы/материалы),
  дата (приоритет — из имени файла; для ведомостей — самая поздняя строка, кумулятивность),
  номер, заголовок.
- **Черновик** — `services/renovation/import/draft.ts`: разбор позиций/строк (таблицы pdfplumber,
  при их отсутствии — построчный текст: многострочные позиции, «Доставка/Подъём», «Всего»),
  итоги, `needsReview`/`warnings` при неполном разборе. Черновики живут в памяти
  (`draftStore.ts`, TTL 30 мин).
- **Эндпоинты** (admin, см. `docs/specification-api.md` §2.5):
  - `POST /api/renovation/pdf` (multipart) — извлечение + классификация → `{ draft }`;
  - `POST /api/renovation/pdf/:id/confirm` — идемпотентность (тип+дата → 409) → запись в БД.
- **Фронтенд:** модалка `RenovationPdfModal.tsx` (admin, кнопка «Импорт PDF» на странице
  «Ремонт»): выбор PDF → загрузка → предпросмотр черновика (тип/дата/позиции/итог/предупреждения)
  → «Подтвердить импорт» → перезагрузка сводки.
- **Ограничения автоматики:** на PDF без линий таблиц разбор построчный и может требовать
  ручной проверки (`needsReview`); fallback — навык `project-renovation-update-from-pdf`.

### 5.1.1. Сохранение загруженных PDF и просмотр в приложении

- **Хранение:** загруженный PDF при подтверждении импорта сохраняется в
  `RENOVATION_DOCS_DIR` (по умолчанию `docs/renovation` относительно CWD бэкенда: dev —
  `backend/docs/renovation`, сервер — `server/docs/renovation`, каталог **сохраняется** при
  деплое, как `data/`). Сервис — `services/renovation/import/pdfStore.ts`:
  - при загрузке (`POST /pdf`) файл кладётся как pending (`docs/.pending/<draftId>.pdf`) и
    переносится в каталог документов при подтверждении (`finalizePdf`);
  - имя файла — детерминированное по классификации (`pdfFileName`):
    `settlement_<works|materials>_<дата>.pdf`, `work_act_<дата>[_<номер>].pdf`,
    `material_order_<дата>[_<номер>].pdf`, `addendum_<дата>.pdf`;
  - осиротевшие pending-файлы вычищаются по TTL (`cleanupPendingPdfs`), при ошибке сохранения
    перенесённый файл удаляется (`discardPdf`).
- **Раздача:** `GET /api/renovation/docs/:file` (под `requireAuth`) отдаёт PDF из каталога
  документов; имя проверяется (только `[a-z0-9._-]`, без выхода за каталог — path traversal),
  400 — некорректное имя, 404 — файл не найден. В БД пишется `pdf_path` =
  `/api/renovation/docs/<file>` (заполняется при подтверждении: `insertRenovationDoc`,
  `insertSettlementAct`, `insertAddendumVersion`).
- **`pdf_path` у записей:** URL приложения `/api/renovation/docs/<file>` — как у
  импортированных документов, так и у записей из seed (на сервере PDF, включая перенесённые
  со статичного архива, лежат в `server/docs/renovation/`). Просмотрщик умеет и «прямые»
  серверные пути (`/projects/...`) — они остались у записей, чьи файлы ещё не перенесены.
- **Перенос существующих PDF (разовая операция на сервере):** файлы, на которые ссылался seed
  через статичный архив (`public_html/projects/renovation/pdf/…`), переносятся в
  `server/docs/renovation/` с именами по тем же правилам (акты/заказы/ведомости —
  `pdfFileName`, смета — `estimate.pdf`, доп. соглашения — `addendum_<дата>_<id>.pdf`), а
  `pdf_path` в БД переписывается на `/api/renovation/docs/<file>`. Статичный архив остаётся
  только с файлами вне БД (дизайн-проект, фото, спецификации). ВНИМАНИЕ: повторный
  `--seed-renovation` восстанавливает `pdf_path` из `.doc-sources` (URL статичного архива) —
  после пересева перенос нужно применить заново.
- **Просмотр:** фронтенд-компонент `components/PdfViewerModal.tsx` (pdf.js / `pdfjs-dist`,
  ленивый чанк): скачивает файл через `fetchFileBytes` (`api/client.ts`; для `/api/*` — с
  обработкой 401), рисует страницы на `<canvas>` с листанием, масштабом и индикатором страницы.
  Ссылки-кнопки на исходные PDF: в «Блоке 2. Материалы» сводки (`RenovationPage.tsx`) и в
  шапках заказов отчёта «Материалы» (`RenovationMaterialsReport.tsx`, `onOpenPdf`).

## 5.2. Применение доп. соглашений к смете (этап 4 — реализовано)

**Проблема.** Импортированные доп. соглашения (`estimate_versions` с `kind='addendum'`) хранят
только свои позиции и итог, но не «встроены» в актуальную смету. Нужно применить соглашение к
`current` с пересчётом итогов и сохранением версии до применения (для аудита/отката).

**Движок диффа** — `services/renovation/addendum.ts` (чистая логика, без Express/SQLite):

- `normalizeName(name)` — нижний регистр, пунктуация `|,.;:()«»"'`/\\` → пробел, схлопывание
  пробелов. Ключ сопоставления позиций.
- `targetSection(section)` — секция «…— дополнительные работы» → базовая («Раздел 5. Электрика
  — дополнительные работы» → «Раздел 5. Электрика»).
- `buildAddendumProposal(current, addendum)` → `{ diffs, newTotal…, needsReview, warnings }`:
  позиции соглашения сопоставляются с `current` по `normalizeName` — точное совпадение →
  `update` (изменение), отсутствие → `new` (добавление); позиции `current`, не затронутые
  соглашением, → `keep` (сохраняются по умолчанию; пользователь может пометить на удаление).
  Пустое наименование позиции → warning.
- `newItemsAfter(current, addendum, removeKeys)` — позиции после применения: `current` в исходном
  порядке, совпавшие — значениями из соглашения (`change='changed'`); новые позиции соглашения
  вставляются в конец своей секции (`change='new'`); **помеченные на удаление не возвращаются**
  (фильтр в шаге добавления новых); сквозная перенумерация 1..N.
- `historyItemsAfter(current, removeKeys)` — историческая копия старой `current`: удалённые
  позиции помечаются `change='removed'`.
- `totalsAfter(current, addendum, removeKeys)` — пересчёт: сумма позиций → «Итого по всем
  разделам» + накладные 5% = «Итого» (`OVERHEAD_PERCENT = 5`).

**Версионирование** — `db/renovationRepository.ts::applyAddendumVersion` (транзакция):

1. старая `current` → `kind='history'`, `date = дата доп. соглашения`,
   `label = "<старый> (до доп. соглашения <label>)"`, позиции — из `historyItemsAfter`;
2. создаётся новая `current` (`date=NULL`, итоги из `totalsAfter`, `addendum_ref = label`
   соглашения), позиции — из `newItemsAfter`.

**Эндпоинты** (admin, `routes/renovation.ts`, детали — `docs/specification-api.md` §2.5):

- `POST /api/renovation/estimate/addendum` — тело `{ addendumId }` → `{ proposal }` (дифф +
  новый итог), без записи;
- `POST /api/renovation/estimate/addendum/confirm` — тело `{ addendumId, removeKeys?: string[] }`
  → применяет и возвращает `{ currentId, total, totalNoOverhead, overhead, itemsCount }` (201).
  Проверки: `addendumId`/`addendum.kind='addendum'`, у соглашения есть `date`, есть `current`.

**Фронтенд:** модалка `AddendumModal.tsx` (admin, кнопка «Доп. соглашение» на странице «Ремонт»):
список соглашений (`GET /estimate/versions`) → выбор → дифф (Было/Стало, метки
изменение/добавление/без изменений) → чекбоксы «Удалить» для позиций `keep` → итоги
(Итого по всем разделам / Накладные 5% / Итого) → «Применить доп. соглашение» → перезагрузка
сводки. API-клиент: `fetchRenovationEstimateVersions`, `fetchRenovationAddendumProposal`,
`confirmRenovationAddendum` (`api/client.ts`).

**Проверено (curl + браузер):** proposal по соглашению №2 — 8 изменений + 54 без изменений,
итог без изменений (соглашение уже встроено в `current`); confirm — старая `current` → `history`

## 5.3. Отчёты из БД (этап 5 — реализовано)

Замена статичных `Reports/report_work.html` и `Reports/report_materials.html`: отчёты строятся
из БД на лету, без ручной/LLM-сборки HTML.

- **«Ход работ»** — `services/renovation/reports.ts::buildWorkReport()` + `GET /api/renovation/reports/work`:
  план = позиции актуальной сметы (`current`), факт = позиции актов работ (суммирование по всем
  актам, сопоставление по `normalizeName`). Каждая строка: план (цена/объём/сумма), факт
  (объём/сумма), отклонение `факт − план` (красный «перерасход», зелёный «экономия»), статус
  (`done` — есть факт и отклонение 0; `partial` — есть факт, но отклонение ≠ 0; `notdone` — факта
  нет). Секции сохраняют порядок сметы; итоги: план/факт/освоение %, счётчики статусов; `asOf` —
  самая поздняя дата документа; сводка взаиморасчётов по работам (последний акт, кумулятивность).
- **«Материалы»** — `buildMaterialsReport()` + `GET /api/renovation/reports/materials`: заказы
  материалов с позициями и итогами (в т.ч. накладные), сводка (кол-во заказов, итого закуплено,
  итого накладных).
- **Фронтенд:** на странице «Ремонт» — ссылки «Ход работ» / «Закупка материалов» в карточках
  «Работы»/«Материалы», отчёты открываются в модальном окне
  (`components/Modal.tsx`, `modal--report`) (`RenovationPage.tsx`, ленивая загрузка
  через `hooks/useRenovationReports.ts` с кэшем);
  компоненты `components/RenovationWorkReport.tsx`, `components/RenovationMaterialsReport.tsx`;
  типы и функции — `api/client.ts` (`fetchRenovationWorkReport`, `fetchRenovationMaterialsReport`).
- **Ограничение автоматики:** сопоставление план↔факт — по точному нормализованному наименованию;
  при разнице формулировок между сметой и актом строка может не «склеиться» (показывается как
  «не выполнено»). Статичный отчёт в таких местах достраивался вручную (LLM). При необходимости —
  словарь синонимов/ручное сопоставление.

## 7. Решения и находки (ADR + факты из данных)

Общие ADR — в `docs/specification.md` (§12, ADR-13…ADR-18). Здесь — факты о данных проекта и
грабли, зафиксированные при импорте:

- **Копейки (×100).** REAL в SQLite неточен; сверка «суммы сходятся» и пересчёт накладных должны
  быть детерминированными. Канон — `domain/money.ts`; в seed-скрипте логика продублирована без
  сборки (как `scripts/users.mjs`).
- **Оба десятичных разделителя.** В PDF/HTML встречаются и запятая (`141 127,88`), и точка
  (`134 407.50`); разделитель тысяч — пробел/неразрывный пробел. Нормализация — в `parseDecimal`.
- **Минус — U+2212 (`−`), не ASCII.** В PDF/HTML отрицательные суммы записаны символом U+2212
  (`−22 832,80`); `parseDecimal` приводит его к ASCII `-` перед разбором.
- **Отрицательные десятичные.** `parseDecimal` трактует знак как знак модуля:
  `−22 832,80` → `-(22832 + 0.80)`, а не `-22832 + 0.80` (иначе получалось `-22 831,20`).
- **Знак «Подотчетные прораба» непоследователен.** В ведомости 17.07 — `+50 000,00`,
  в 06.08 — `−50 000,00`; оба уменьшают баланс на 50 000. Верификация не зависит от знака
  (строки-подсуммы пропускаются; строка «Всего» проверяется по собственной арифметике
  `внесено − использовано = баланс`).
- **Неявные накладные в заказах материалов.** Итог «с учетом накладных расходов» не содержит
  отдельной строки накладных: `накладные = итог − сумма позиций` (10% у заказов №1–№3, 0% у №4).
  Сохраняется вычисленное значение; верификация допускает ровно 0% или 10%.
- **«Доставка»/«Подъём» — позиции заказа.** В заказах материалов это обычные строки таблицы
  (без цены/количества), сохраняются как позиции.
- **Кумулятивные ведомости.** В расчёт отчётности идёт только последний акт на тип (по `date`).
  Строка-подсумма «Подотчетные прораба» имеет только баланс и уменьшает накопленный баланс
  (учтено в верификации).
- **Два варианта разметки секций.** В смете секции — `<div class="section">`; в актах и доп.
  соглашениях — обычный `<div>` + `.section-title`. Парсер `parseTablesWithSections` находит
  таблицы и назначает им ближайший предшествующий `section-title`. Шапки таблиц (`<th>`) в данные
  не идут.
- **HTML-парсинг — только в seed-скрипте.** После наполнения БД новые данные попадают через
  приложение (импорт PDF, `pdfplumber`), а не из HTML. Источник истины — БД, а не HTML.
- **Репозиторий на этап API.** `db/renovationDatabase.ts`/`db/renovationRepository.ts` создаются
  на этапе 2 (read-API), схема — из блока `SCHEMA` seed-скрипта (единый источник).
- **Prettier на Windows.** `npm run format` = `prettier --write .` переписывает все файлы CRLF→LF,
  создавая шум в `git status` (M без содержательных изменений). Форматировать только изменяемые
  файлы. `.prettierignore` исключает `.venv/`, `dist/`, `node_modules/`, `temp/` (иначе локальный
  Python-venv ломает запуск format).
- **Дата доп. соглашения в seed (этап 4).** `dateFromEstimateName` долго не обрабатывал префикс
  `estimate_add_` — дата аддендумов оставалась `NULL` (а для версионирования «до доп.
  соглашения» дата обязательна). Исправлено: `/estimate_(?:add_)?(\d{4}-\d{2}-\d{2})/`.
- **Помеченные на удаление не должны возвращаться (этап 4).** В первой версии `newItemsAfter`
  позиция, удалённая `removeKeys` и присутствующая в доп. соглашении, заново добавлялась в шаге
  «новые позиции» (итог не менялся). Исправлено: шаг добавления новых фильтрует `removeKeys`.
- **Дубликаты нормализованных имён.** В смете есть повторяющиеся наименования
  («Грунтование стен/откосов перед оштукатуриванием» — поз. 17 и 21, секция «Стены»; то же для
  «Установка маяков…», «Укладка керамогранита…», «Затирка швов…»). Сопоставление по
  `normalizeName` в таком случае берёт последнее совпадение (Map). В UI-таблице диффа ключи
  строк — по индексу, чтобы не было дублей React-ключей.
- **Версионирование транзакцией.** `applyAddendumVersion` выполняет UPDATE старой `current` +
  перезапись её позиций + INSERT новой `current` + позиций в одном BEGIN/COMMIT (ROLLBACK при
  ошибке) — старое и новое состояние никогда не видны «наполовину».
